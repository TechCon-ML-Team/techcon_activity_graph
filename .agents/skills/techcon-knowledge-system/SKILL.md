# Knowledge System — куда кладём знания в репозитории

Перед тем как сохранить план, спецификацию, ретро, заметку или любой другой текстовый
артефакт работы — определи его тип по таблице ниже и положи в правильное место. Это не
эстетика: агент следующей сессии находит знание только там, где договорено его искать —
не по памяти и не полнотекстовым поиском по всему дереву.

---

## Типы знания и где им место

| Тип | Куда | Загружается |
|---|---|---|
| Архитектурный контекст (стек, ключевые файлы, устройство репозитория) | `context.md`-подобный файл в корне или в каталоге агентского контекста репозитория | автоматически на старте сессии |
| Процессные правила (формат коммитов, что нельзя трогать без согласования) | `rules.md`-подобный файл там же | автоматически на старте сессии |
| Жёсткие технические ограничения (обратная совместимость, запрет на зависимости, миграции только через X) | `constraints.md`-подобный файл там же | автоматически на старте сессии |
| Критерии готовности задачи | `done-criteria.md`-подобный файл там же | автоматически на старте сессии |
| Повторно применимый приём работы (скилл) | каталог `skills/<slug>/SKILL.md` репозитория | по явному запросу — не грузится весь каталог сразу |
| История конкретной задачи (спецификация, ретро) | каталог с логами задач (`tasks/<id>/` или аналог) | по запросу, при разборе истории |
| Бэклог, список текущих задач | отдельный файл-справка | по запросу, не автоматически |

**Правило разделения `constraints.md` vs `rules.md`**: если нарушение ограничения ломает
что-то архитектурно или требует согласования команды — это `constraints.md`. Если это
вопрос рабочего процесса (порядок коммитов, кто мержит) — это `rules.md`.

## Не мусори в корень репозитория

Без явного согласования владельца **запрещено**:

- создавать произвольные `.md`-файлы в корне репозитория (кроме `README.md`,
  `CHANGELOG.md`, `LICENSE`, и файлов головы репозитория типа `AGENTS.md`);
- создавать директории вида `dev/`, `notes/`, `ai-artifacts/`, `scratch/` в корне;
- оставлять промежуточные артефакты (черновики плана, временные заметки) вне
  выделенного для них каталога.

Каждый такой артефакт имеет законное место из таблицы выше — если места нет, это повод
спросить владельца, а не изобретать новый каталог в корне.

### Детектируемые паттерны мусора

При аудите репозитория ищи:

- **root MD clutter** — файлы `*.md` в корне сверх разрешённого списка;
- **MD-heavy директории** — каталог, где больше ~70% файлов это `.md` без явного
  назначения (типичные имена: `dev/`, `notes/`, `docs-draft/`, `ai/`);
- **чужие AI-каталоги** — конфиги других инструментов, оставленные по инерции
  (`.cursor/`, `.windsurf/`, `.aider*` и подобные), если репозиторий их не использует;
- **осиротевшие артефакты задач** — файлы вида `PLAN.md`, `SPEC.md`, `TODO.md` в корне,
  не привязанные ни к одной текущей задаче.

Найденное — не удаляй молча, предложи переместить в подходящий каталог из таблицы или
явно спроси владельца.

## On-demand скиллы: принцип

Скилл — это инструкция для агента на естественном языке, не рантайм-код. Загружай
конкретный скилл только когда его тема релевантна текущей задаче — не инжектируй все
скиллы репозитория в контекст сразу, это тратит токены без пользы.

Не создавай новый скилл под разовый сценарий или под то, что на самом деле требует кода,
а не текстовой инструкции — это не знание, это функциональность.

---

## Откуда берутся новые скиллы

```
Повторяемый паттерн замечен в нескольких задачах
  → агент выделяет общий приём (вручную или при ретроспективном разборе истории задач)
  → оформляет как skills/<slug>/SKILL.md по принятому в репозитории формату
  → скилл становится доступен для будущих сессий
```

Источник для такого разбора — история задач (спецификации, ретро, логи) в каталоге,
выделенном под неё этим репозиторием. Если повторяющийся паттерн виден в нескольких
задачах подряд — это кандидат на скилл; единичный случай — нет.

## Проверка перед сохранением

Прежде чем писать новый файл-артефакт, ответь на два вопроса:

1. Какого он типа (см. таблицу) — и, значит, куда он должен лечь?
2. Не создаю ли я новый корневой `.md`/каталог там, где уже есть подходящее место?

Если ответ на оба вопроса ясен — сохраняй. Если нет — это сигнал остановиться и уточнить
у владельца репозитория, а не изобретать структуру на ходу.
