# Заполнение/обновление ТЗ (xlsx по форме организации)

Портируемая директива, не программа — читается и исполняется любым агентным
harness'ом построчно, обычными командами оболочки и чтением файлов.
Разделение код/агент: числа и структурные факты (парсинг xlsx, diff, чтение
метаданных) — код (`tz_xlsx_tools.py` или его аналог в целевом репозитории);
содержание ячеек и решение «что писать в каком разделе» — агент.

## Goal

Заполнить или обновить xlsx-книгу ТЗ по канонической форме проекта
(шаблон + документ с правилами оформления), соблюдая:
разделение продукт/техника внутри ячейки, цвет/курсив как сигнал состояния
поля, явная атрибуция автора ответа, честное «пусто» вместо придуманного
ответа.

## Область действия

**Делает:** заполняет новую книгу по шаблону для нового проекта; обновляет
существующую книгу новыми ответами, сохраняя уже заполненные разделы
нетронутыми, если не попросили иначе; сравнивает две версии одного ТЗ
(`tz_xlsx_tools.py diff` или эквивалент), чтобы показать, что реально
изменилось.

**НЕ делает:** не читает материал из внешнего облачного хранилища без
проверки свежести источника (см. Фазу 0), если владелец прямо предупредил,
что хранилище может нести неактуальные данные; не пишет готовую книгу
обратно во внешнее хранилище (система записи — репозиторий проекта, не
Drive/Confluence/etc.); не придумывает ответ за раздел, явно отданный
другому человеку на заполнение — оставляет серым курсивом с пояснением.

## Фаза 0 — Проверка свежести источника (ОБЯЗАТЕЛЬНА, если материал из внешнего хранилища)

Если владелец явно предупредил, что во внешней папке (Google Drive,
Confluence, общий диск) есть неактуальные данные — доверие ОДНОМУ сигналу
свежести (например, только mtime/modifiedTime) неприемлемо. Инструмент
может согласовываться сам с собой, а не с предметом (файл выглядит
«свежим» по метке времени, оставаясь устаревшим по содержанию).

Перед тем как использовать файл, скачанный извне, как основу, собери ТРИ
независимых сигнала:

1. **Метаданные хранилища** (`modifiedTime` и аналоги) — когда файл
   последний раз трогали физически.
2. **Версия/дата в тексте самой книги** — если в шаблоне организации есть
   явная строка версии/даты на листе описания, свериться с ней.
3. **Совпадение состава с фактическим репозиторием проекта** — разделы/листы
   «Модуль · X» должны соответствовать реальным подсистемам репозитория
   (сверить с деревом файлов/README), не быть шаблонными заглушками из более
   старой версии формы.

Если сигналы РАСХОДЯТСЯ (например, метаданные свежие, но версия в тексте —
старая, или состав модулей не совпадает с репозиторием) — ОБЯЗАТЕЛЬНО
спросить владельца, какой файл считать источником истины, а не выбирать
более удобный сигнал самостоятельно.

## Working rules

1. **Каноническая форма проекта** — обычно xlsx-шаблон, зафиксированный в
   стандартах репозитория (например, `standards/tz/ТЗ_шаблон_*.xlsx`) плюс
   документ с правилами оформления (например,
   `standards/tz/ПРИНЦИПЫ_ОФОРМЛЕНИЯ_ТЗ.md`). Типовые листы: «Описание
   проекта», «Модуль · <имя>» (несколько листов под реальные подсистемы
   проекта — не обязательно совпадают с примером в шаблоне), «Доступы и
   ресурсы», «Решение команды», «Проверка при сдаче».
2. **Разделение продукт/техника внутри ячейки** — продуктовый смысл, пустая
   строка-разделитель, техническая реализация — в одной ячейке, не двух
   отдельных.
3. **Цвет/курсив — сигнал, не декор.** Чёрный не курсив = финальный ответ.
   Серый курсив = пример/гайдлайн ИЛИ явно отданный другому человеку
   раздел — никогда не оставлять серый курсив там, где уже есть настоящий
   ответ.
4. **Атрибуция.** Каждый содержательный ответ — от кого он и когда, по
   правилу атрибуции документа оформления проекта — не анонимный текст.
5. **Обновление, не пересоздание.** Если книга уже существует в
   репозитории, после правки прогони инструмент сравнения версий (diff),
   чтобы предъявить, что реально изменилось — не переписывай книгу с нуля
   молча.

## Authority rules

- Не додумывай ответ за раздел, у которого есть явный автор (человек),
  указанный в примечании ячейки — оставь плейсхолдер.
- Готовая книга коммитится в репозиторий проекта; внешнее облачное
  хранилище — только источник ЧТЕНИЯ материала, не место записи готовой
  книги.
- При любом расхождении сигналов свежести (Фаза 0) — вопрос владельцу, не
  тихий выбор.

## Minimum output

- Готовая или обновлённая книга ТЗ в репозитории проекта.
- Если материал брался из внешнего хранилища — короткая заметка (в
  описании коммита или отдельным файлом рядом), какие три сигнала
  свежести проверены и каким было решение.
- Вывод инструмента diff (старая версия → новая) перед коммитом
  обновления — приложить к описанию изменения, не полагаться на память о
  том, что менялось.

## Anti-patterns

- Скачать файл из внешнего хранилища и сразу использовать его как источник
  истины без проверки хотя бы одного сигнала свежести — та самая находка,
  из-за которой Фаза 0 обязательна.
- Оставить серый курсив «для примера» рядом с уже написанным настоящим
  ответом — читатель не поймёт, что из этого реальный ответ.
- Придумать правдоподобный ответ за человека, которому явно отдан раздел
  на заполнение, вместо честного плейсхолдера.
