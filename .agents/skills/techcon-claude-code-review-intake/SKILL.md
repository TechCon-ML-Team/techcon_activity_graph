# Intake результата ревью

## Когда применять

Сразу после того как получен сигнал «ревью готово» — независимо от того, кто
его написал (другая модель, человек-ревьюер, отдельный шаг пайплайна).
Работает с любым файлом ревью, у которого есть YAML-frontmatter с полем
`verdict` (по умолчанию ищи `review.md` в директории текущей задачи, но имя
файла может быть любым — бери из контекста задачи).

## Шаги

### 1. Найди и прочитай файл ревью

Если файл не найден:
> "Файл ревью не найден. Убедись, что ревью действительно завершено, и
> проверь путь, который был указан при запросе ревью."

### 2. Извлеки verdict

Значения из YAML-фронтматтера:
- `approved` → реализация разрешена;
- `changes-requested` → нужны правки;
- `needs-discussion` → открытые вопросы требуют решения пользователя;
- `critique` → конструктивная критика (не блокер).

Дополнительно проверь поле вида `notVerified` (или аналог) — сколько пунктов
ревьюер не смог проверить.

### 3. Действуй по verdict

#### approved

```
✓ Ревью пройдено. Продолжаем реализацию.

Одобренные аспекты:
[из секции "Одобренные аспекты"]

Замечания к учёту (non-blocking):
[рекомендации, если есть]

Не проверено ({notVerified}):
[если есть — прими к сведению, при необходимости проверь сам]
```

Переходи к реализации (следующий шаг задачи).

#### changes-requested

```
✗ Ревью требует правок.

Блокеры ({N}):
[список блокирующих замечаний]

Следующий шаг: обновить описание задачи/спецификацию → запросить повторное ревью.
```

Обнови описание задачи с учётом блокеров, затем повтори запрос ревью.

#### needs-discussion

```
⚠ Открытые вопросы требуют решения.

Вопросы от ревьюера:
[список открытых вопросов]
```

Задай вопросы пользователю. После ответов зафиксируй решения в описании задачи.

#### critique

```
📋 Критика получена. Блокировки нет.

Слабые места ({N}):
[список слабых мест]

Не проверено: {notVerified}
```

Для каждого слабого места прими решение: учесть его в задаче или
аргументированно отклонить. Реализация продолжается — `critique` не блокирует.

### 4. Обработай "не проверено"

Если непроверенных пунктов больше нуля — реши, критично ли это для текущей
задачи:
- критично → получи недостающие доступы/данные, запроси повторное ревью
  только для непроверенных пунктов;
- некритично → зафиксируй как known-unknown в описании задачи и продолжай.

### 5. Обнови статус задачи

Отметь в трекере задачи (issue/тикет/файл статуса), что ревью получено и
обработано — например, переведи статус `pending review` → `reviewed`.

### 6. Залогируй результат

Зафиксируй итог ревью там, где в проекте принято вести журнал работы по
задаче (лог изменений, комментарий в тикете, файл истории):

```markdown
## {ISO-8601} — Code Review Intake

- Verdict: {verdict}
- Blockers: {N}
- Critique items: {N}
- Not verified: {N}
- Review source: {путь или ссылка на файл ревью}
```

## Output contract

- Verdict применён;
- `approved/critique`: работа над задачей продолжена;
- `changes-requested`: описание задачи обновлено с учётом блокеров;
- `needs-discussion`: пользователь получил открытые вопросы;
- статус задачи обновлён на «ревью обработано».
