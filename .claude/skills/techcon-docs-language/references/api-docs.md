# справочник API — структура

```
# <Название сервиса> — справочник API
## общая информация      версия X.Y.Z, ссылки на ReDoc и openapi.json
## среды                 прод, дев-стенд, локальная
## аутентификация        метод + матрица защиты (эндпоинт, метод, нужен ли токен)
## общие ограничения     нагрузка (число или «без ограничений»), размер запроса, время ожидания
## формат ответов        бизнес-ответ, ошибка, проверка состояния, статус асинхронной задачи
### коды ошибок          код, HTTP, описание
## эндпоинты             описание, аутентификация, таблица полей, пример ответа, ошибки
## сквозной сценарий     curl и Python httpx
```

Правила:

1. Бизнес-ответ: `{"ok": true, "data": {...}}`; ошибка: `{"ok": false, "error": {"code", "message", "detail"}}`,
   `detail` есть всегда (объект или `null`), `message` по-русски.
2. Без обёртки: `GET /health`, `GET /ready`, статус асинхронной задачи, бинарные файлы,
   HTML, SSE, `204`.
3. Статус существующей задачи всегда `200`, состояние в поле `status`; нет задачи — `404`.
4. Основной читаемый источник — ReDoc на `/docs`; `openapi.json` — машинный источник.
5. Ограничения (`401/404/422/429/503`, конечные статусы, срок хранения, роль webhook)
   совпадают в справочнике, живой спецификации и портале. Расхождение — дефект.
6. Примеры запросов синтаксически верны и работают при копировании; заглушка, не
   проходящая контракт, считается дефектом.
7. Тесты документации закрепляют коды, маршруты, поля и сроки, а не английские фразы.

Проверка качества (пять критериев): минимум англицизмов; ноль внутренней кухни (имена
контейнеров, переменные окружения, внутренние хосты и порты, ссылки на процесс выкатки);
соответствие живой спецификации один к одному; рабочие примеры; лаконичность.

Плохо: «дождитесь, пока обработчик на внутреннем хосте подхватит задачу; подставьте
`REDIS_URL` в compose». Хорошо: «обработка асинхронная; опрашивайте статус задачи каждые
2 секунды».
