# Доступ к инфраструктуре

## Базовые правила

- Видимую в репозитории истину о доступах трактуй как **метаданные без секретов**, не как хранилище секретов.
- Предпочитай **локальные (на машине оператора) держатели секретов**:
  - `~/.ssh/*`
  - локальная авторизация/сессия cloud CLI
  - локальный VPN-клиент/сессия
  - локальная связка ключей / менеджер секретов
- Короткоживущие агентские SSH-ключи допустимы, если они живут в локальных держателях секретов или в `ssh-agent` и не коммитятся, не печатаются и не копируются в документы/промпты репозитория.
- Никогда не печатать и не коммитить приватные ключи, сырые токены, VPN-секреты, auth-блобы или вставленный материал учётных данных.
- Предпочитай существующие локальные алиасы/конфиг/runbook'и запомненной по памяти топологии.
- Предпочитай явный дескриптор доступа репозитория без секретов или runbook запомненной по памяти project-специфичной топологии.

## Первая классификация

Прежде чем делать что-либо, классифицируй режим доступа:
- `ssh-direct` — прямой SSH
- `ssh-bastion` / `proxyjump` — через бастион/ProxyJump
- `ssh-internal-via-public-controller` — внутренний SSH через публичный контроллер
- `cloud-cli-first` — сначала cloud CLI
- `vm-start-then-connect` — сначала поднять ВМ, потом подключиться
- `vpn-then-ssh` — сначала VPN, потом SSH
- `proxy-required` — обязателен прокси
- `user-assisted-only` — только с участием человека
- `unsupported-without-human` — без человека не поддерживается

Если режим неясен — сначала выводи его из документов/конфига репозитория, только потом задавай точечные вопросы.

## Что относится к «истине репозитория»

Разрешено в документах/шаблонах репозитория:
- имена алиасов
- имена хостов/референсов
- описание пути через jump-хосты
- идентификаторы облака/папки/проекта, если это безопасно
- ожидаемое имя пользователя/логина
- требуемые локальные инструменты
- требование подтверждения человеком
- команды валидации
- известные классы отказов
- заметки о владельце / эскалации
- метаданные короткоживущего ключа только как класс хэндла/алиаса/пути, никогда как сам секретный материал

Запрещено в документах/шаблонах репозитория:
- сырые приватные ключи или тела ключей
- сырые токены
- значения секретов из окружения
- полные наборы VPN-учётных данных
- готовые к копипасте привилегированные учётные данные

## Паттерн принятия решения

### 1. Сначала читай истину
Ищи, в таком порядке:
1. локальный документ/дескриптор доступа репозитория
2. канонический runbook / поверхность стандартов, если у репозитория такая есть
3. локальные алиасы SSH-конфига / стабильные имена ключей
4. инвентарь облака / метаданные, видимые через CLI

### 2. Реши, может ли агент действовать автономно
Агент обычно МОЖЕТ действовать автономно:
- read-only инвентаризация облака
- проверки достижимости по SSH
- проверки отпечатков ключей
- использование локальных короткоживущих SSH-ключей или identity `ssh-agent` для одобренных проверок доступа
- нормализация локального конфига
- обновление документов/шаблонов репозитория
- черновик инвентаря/отчёта о доступах без секретов

Агент ОБЯЗАН остановиться или явно запросить подтверждение, когда действие:
- раскрывает или вставляет секреты
- мутирует боевые полномочия доступа prod/облака/SSH широко или неясным образом
- ротирует учётные данные/ключи в обход одобренного процесса пула короткоживущих ключей
- включает/выключает VPN/прокси/auth-провайдеров
- запускает/останавливает/меняет дорогую или рискованную инфраструктуру без ясно одобренного объёма
- затрагивает неизвестный радиус поражения в проде

### 3. Предпочитай самый тонкий полезный механизм
Порядок предпочтения:
1. только документы/runbook/шаблон
2. процедура, описанная напрямую оператору
3. локальная CLI-команда с явным одобрением, если это чувствительно
4. узкий read-only MCP только если документов/CLI недостаточно
5. кастомный мутирующий MCP только как последнее средство

## Формат отчёта

При резюмировании работы по доступам разделяй:
- **Прямое свидетельство**
- **Вывод**
- **Неизвестное**
- **Следующее действие оператора**

## Паттерн обновления репозитория

Если работа даёт переиспользуемый урок про доступ:
- обнови локальный дескриптор доступа репозитория без секретов или документ доступа
- обнови канонический runbook/поверхность стандартов, если изменилась видимая в репозитории истина о доступах
- пиши только минимально необходимый артефакт отчёта — избегай markdown-спама
- предпочитай один канонический файл плюс короткие локальные ссылки

## Анти-паттерны

- Считать запомненные IP/хосты истиной, когда есть более свежий инвентарь
- Вставлять секреты в промпты/документы ради удобства
- Строить общий секрето-несущий SSH/cloud MCP до того, как стабилизировалась доктрина
- Позволять каждому репозиторию изобретать свою политику хранения учётных данных
- Считать неразрешённый доступ поводом угадывать и продолжать вслепую мутировать инфраструктуру
