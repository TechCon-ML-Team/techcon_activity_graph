# Linear governance — explain-then-mutate

Linear — внешняя поверхность планирования команды: любая мутация видна людям и меняет их
картину работы. Governance-правило одно: **сначала объясни, потом меняй.** Чтение Linear
свободно, без ограничений.

## Принцип

**explain-then-mutate:** перед КАЖДОЙ мутацией Linear выведи пользователю:
1. **Что** изменится — конкретный issue/поле/статус (id + текущее → новое значение).
2. **Зачем** — какое решение или исход это отражает.
3. **Обратимость** — легко ли откатить.

Затем жди согласия («да/продолжай»). Согласие на ОДНУ мутацию не распространяется на
следующую — каждая мутация подтверждается отдельно, по границе одного логического решения,
а не по числу вызовов API. Молчаливая пакетная мутация Linear запрещена.

## Чтение (без объяснения)

```
list_issues / get_issue / list_projects / list_cycles / get_project
```

Инструменты чтения Linear используй свободно — ориентируйся в текущем состоянии перед тем,
как предлагать изменения.

## Мутация (после explain + согласия)

```
save_issue / save_status_update / save_project / save_comment
```

Допустимая автономность БЕЗ отдельного подтверждения — только нейтральные,
очевидно-ожидаемые действия, прямо вытекающие из уже согласованного исхода: например
комментарий-ссылка на коммит к issue, по которому только что подтверждено завершение
работы. Смена статуса, переназначение, закрытие, перенос между проектами — всегда
explain-then-mutate, без исключений.

## Связь коммит ↔ задача

Если работа отслеживается и в git, и в Linear, держите их согласованными: закрытие исхода
задачи (готово / передано дальше / эскалировано) — повод предложить синхронный апдейт
статуса Linear, но и этот апдейт проходит через explain-then-mutate, не выполняется
автоматически вместе с git-коммитом.

## Минимальный вывод при использовании навыка

- какие issue/поля прочитаны для ориентира;
- для каждой предложенной мутации: что → зачем → обратимость;
- получено ли явное согласие перед мутацией;
- фактический результат (id issue, новый статус) после применения.

## Анти-паттерны

- Мутация Linear «по ходу» без объяснения — нарушение governance.
- Пакетная смена статусов нескольких issue по одному «да».
- Создание issue-дублей без предварительного чтения существующих (`list_issues` сначала).
- Трактовка ЧТЕНИЯ как требующего подтверждения — это тормозит без пользы, governance
  касается только мутаций.
