# Практика тестирования — покрытие «код без тестов» и стиль golden-тестов

## Правило присутствия, не построчное покрытие

В организации действует не «каждому `foo.py` — свой `test_foo.py`», а более
грубое и дешёвое правило: если PR/сессия трогает код-подобные пути, но НИ
ОДИН путь под `tests/` — это нарушение. Если хотя бы один тестовый путь
тоже изменён — требование считается выполненным целиком, без проверки, что
именно этот код покрыт. Это осознанное ограничение (см. докстринг
`hooks/tests_coverage.py`): построчное сопоставление test↔source потребовало
бы понимания структуры каждого репозитория; правило ловит самый частый и
самый дёшево обнаруживаемый случай — «код поменяли, ни одного теста не
тронули».

**Практический вывод: пиши тест в том же коммите/PR, что и код**, не
откладывай на «потом» — правило проверяет факт изменения `tests/**` в том
же дифе, не отдельным последующим PR.

## Что считается «код-подобным путём»

Всё, что НЕ попадает под явный allowlist не-кода:
- пути с префиксом `docs/`, `.github/`, `audit/`, `dashboards/`, `canon/`;
- файлы с расширением `.md .json .lock .txt .toml .cfg .ini .gitignore`;
- dotfiles (любой сегмент пути начинается с `.`).

Важно: `.yaml`/`.yml` **не** в списке исключений — файлы вроде
`policy/*.yaml`, `models/registry.yaml`, `roles/*.yaml` реально меняют
поведение/маршрутизацию и считаются код-подобными. Если меняешь такой
YAML-конфиг без единого теста под `tests/` — хук это отметит.

Тестовым путём считается любой путь, где `tests` — целый сегмент (не
подстрока) — это работает и для корневого `tests/`, и для per-package
раскладки вида `pkg/tests/test_x.py`.

## Как это проверяется сегодня — режим observe, не enforce

Реализация — `hooks/tests_coverage.py` (чистая функция `check_paths()` +
CLI) и Stop-хук-консьюмер `hooks/rules/tests_coverage_stop.py`. Три кода
выхода (единый контракт харнесса): `0` — код без нарушения (либо нет
код-подобных изменений, либо тесты тоже изменены), `1` — нарушение (код
изменён, тесты — нет), `2` — не удалось измерить (не git-репозиторий, git
упал, явный список путей не передан).

`MODE = "observe"` — правило **не блокирует** ни коммит, ни остановку
сессии. Stop-хук печатает совет в stderr, видимый человеку/логу, но
никогда не возвращает `decision: block` — блокирующая семантика Stop-хука
означала бы «не дай агенту остановиться», а это правило намеренно не
enforce (переход `observe → enforce` в плане организации требует
собственного критерия — ложные срабатывания ≤10% по журналу — и ещё не
наступил). **Не воспринимай "observe" как "можно игнорировать" — это
намеренная промежуточная стадия**, а не мёртвый код: несоблюдение всё равно
видно в логе и годится как основание для последующего enforce.

Diff для Stop-хука считается против `origin/develop` (merge-base), с
fallback на `HEAD~1`, потому что одна сессия обычно несёт несколько
коммитов, а не один — сравнение с последним коммитом занизило бы охват.

## Проверка вручную

```bash
python3 -m hooks.tests_coverage --repo-root . --against origin/develop
# или явный список путей (для CI без git-дерева):
python3 -m hooks.tests_coverage --paths cli/foo.py cli/bar.py
```

Перед тем как звать `--against <ref>` с непроверенным значением — не
передавай ref, начинающийся с `-` (git интерпретирует его как свою опцию, а
не как ref); модуль сам отклоняет такой ввод.

## Стиль тестов в этом репозитории — golden-тесты

Образец — `tests/golden/test_tests_coverage.py` и
`tests/golden/test_tests_coverage_stop.py`. Общий паттерн golden-тестов
организации:

- Тестируется **чистая функция** (`check_paths`, `check_message` и т.п.)
  отдельно от CLI/IO-обвязки — так проверка не требует подготовленных
  файлов на диске и не зависит от состояния git-репозитория.
- Для функций, реально трогающих git/subprocess (`check_stop`,
  `git_changed_paths`) — тест либо создаёт временный git-репозиторий
  (`tmp_path` + `git init`/`git commit`), либо подменяет `subprocess.run` для
  синтетических сценариев (зависший процесс, отсутствующий в PATH `git`).
- Каждый найденный живым ревью баг фиксируется отдельным тест-кейсом с
  комментарием, что именно он ловит (см. комментарии «Найдено независимым
  ревью» в `hooks/tests_coverage.py` — у каждого есть тест-двойник).
- Тест на полный контракт трёх кодов выхода (`0`/`1`/`2`) — отдельные кейсы
  на каждый код, не только happy path.
- Импорт — из модуля напрямую (`from hooks import tests_coverage`), этот
  репозиторий не пакетирован (`testpaths = ["tests"]`, нет `src/`).

## Когда писать тест

- Новая функция/модуль с содержательной логикой (не однострочный
  проброс аргументов) — тест обязателен в том же коммите.
- Найден баг живым ревью или в проде — тест, воспроизводящий именно этот
  баг, пишется ДО исправления (или вместе с ним), чтобы регрессия была видна в
  дифе, а не только в описании PR.
- Правка существующего поведения (не только багфикс) — существующие тесты
  должны либо остаться зелёными, либо быть осознанно обновлены вместе с
  причиной изменения в теле коммита.

## Чего это не заменяет

Зелёные тесты доказывают, что код делает то, что проверяет тест — они не
доказывают фактов о состоянии внешнего мира (см. `techcon-fact-verification`
для этого класса проверок). Присутствие теста под `tests/` в дифе — сигнал
наблюдательного хука, не гарантия качества покрытия: хук не проверяет, что
именно новый код протестирован, только что тестовый путь вообще тронут.
