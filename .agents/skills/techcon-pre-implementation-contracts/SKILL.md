# Pre-Implementation Contracts — контракты перед реализацией

Перед написанием кода нужно сформулировать и зафиксировать все применимые
контракты. Неполный контракт — это разрешение начать реализацию, не понимая
последствий: какую проблему решаем, где источник истины, что система будет
уметь и не уметь, как это протестировано, как это деплоится и как это
наблюдать в проде.

## Когда применять

Перед реализацией любой нетривиальной задачи: новая фича, изменение
существующего поведения, миграция данных или конфига, изменение
инфраструктуры. Не обязательно для тривиальных правок (опечатка, точечный
фикс без изменения контракта поведения) — в этом случае явно укажи, что
контракты не применимы, и почему.

Заполняй только применимые секции. Неприменимую секцию не пропускай молча —
пиши `не применимо: [причина]`, чтобы было видно, что решение осознанное, а
не забытое.

## Контракты

### 1. Problem Contract — что именно решаем

```
ПРОБЛЕМА: [одно предложение: что сломано или чего не хватает]
МЕТРИКА УСПЕХА: [как поймём, что решено, конкретно и измеримо]
КОРНЕВАЯ ПРИЧИНА: [почему проблема существует, не симптом]
НЕРЕШАЕМОЕ: [что явно вне scope этой задачи]
```

### 2. Source-of-Truth Contract — где истина

```
ИСТИНА: [canonical файл/таблица/сервис, который является источником правды]
НЕ ИСТИНА: [что кажется источником, но им не является]
СИНХРОНИЗАЦИЯ: [как истина распространяется между компонентами]
```

### 3. Capability Contract — что умеет система

```
МОЖЕТ: [что система умеет делать после реализации]
НЕ МОЖЕТ: [явные ограничения текущей реализации]
ПРЕДУСЛОВИЯ: [что должно быть верно перед вызовом]
ИНВАРИАНТЫ: [что всегда остаётся верным во время работы]
```

### 4. TDD Contract — как тестируем

```
UNIT: [что тестируем изолированно, какие граничные случаи]
INTEGRATION: [какие взаимодействия между компонентами]
E2E: [golden path + критичные сценарии ошибок]
НЕТЕСТИРУЕМОЕ: [что не покрываем и почему]
GATE: [тесты должны быть RED перед реализацией, GREEN после]
```

### 5. Migration Contract — как переходим

```
ОБРАТНАЯ СОВМЕСТИМОСТЬ: [нарушается / сохраняется / не применимо]
ДАННЫЕ: [нужна ли миграция данных, схемы, конфигов]
ROLLBACK: [как откатиться, если что-то пойдёт не так]
ПОРЯДОК: [последовательность шагов деплоя]
```

### 6. Deploy/Config Contract — как разворачиваем

```
ENV VARS: [новые переменные окружения, их значения по умолчанию]
КОНФИГИ: [изменения в конфигурационных файлах]
ИНФРАСТРУКТУРА: [нужны ли изменения в docker-compose, k8s и т.п.]
FEATURE FLAGS: [нужны ли флаги для постепенного ввода]
```

### 7. Observability Contract — как наблюдаем

```
ЛОГИ: [что логируем, уровень, формат]
МЕТРИКИ: [какие метрики добавляем или изменяем]
АЛЕРТЫ: [на что нужны алерты]
ОТЛАДКА: [как диагностировать, если что-то сломается в продакшене]
```

## Output contract

Зафиксируй все заполненные контракты в описании задачи, PR или отдельном
файле спецификации до начала кодирования — там, где команда и ревьюер увидят
их раньше кода. Пустые секции — только с явным `не применимо: [причина]`,
никогда без объяснения.
