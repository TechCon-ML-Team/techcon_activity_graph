# YC CLI — безопасные мутации

Используй этот скилл всегда, когда задача затрагивает мутацию ресурсов Yandex Cloud через `yc`.
Чтение (`list`/`get`/`--format`) безопасно и guard не требует. **Любая мутация**
(`create`/`update`/`delete`/`start`/`stop`/`add`/`remove`/`attach`/`detach`) обязана пройти
через guard ниже — без исключений и без «в этот раз явно можно».

## Источник истины по флоту

Перед мутацией сверься с актуальным описанием флота: файлом инвентаря инфраструктуры
(cloud-id, folder-id, список ВМ и сетей — обычно `INFRA.yaml` или эквивалент в
инфраструктурном репозитории организации) и гайдом по доступам (SSH-ключи, алиасы).
Если такого файла в проекте нет — источник истины сначала нужно найти, а не восстанавливать
id по памяти или из старого чата.

## 0. GUARD — allowlist cloud/folder (ОБЯЗАТЕЛЬНО перед мутацией)

Перед КАЖДОЙ мутирующей командой выполни три шага:

1. **Определи целевой scope команды** — какой cloud-id и folder-id она затронет:
   ```bash
   yc config list                       # текущий профиль: cloud-id, folder-id
   ```
   Если команда несёт `--folder-id`/`--cloud-id` явно — берём их, иначе scope = профиль.

2. **Сверь с allowlist из источника истины.** Разрешены ТОЛЬКО cloud/folder, явно
   перечисленные в инвентаре инфраструктуры проекта. Если целевой id не в allowlist —
   **СТОП**, не выполняй, эскалируй оператору-человеку с явным описанием: какая команда,
   какой id, почему он не найден в allowlist.

3. **Подтверди обратимость.** Деструктив (`delete`/`stop` prod-ВМ, удаление диска) —
   требует явного подтверждения оператора перед выполнением. Создание/обновление в
   dev-окружении из allowlist — обратимо, без предварительного подтверждения, но с
   обязательной фиксацией наблюдаемого результата после выполнения.

## 1. Чтение (без guard)

```bash
yc compute instance list
yc compute instance get --name {name}
yc dns zone list
yc vpc network list
yc lockbox secret list
```

## 2. Мутация (после guard §0)

```bash
# пример: запуск on-demand GPU-ВМ (обратимо, dev/prod folder из allowlist)
yc compute instance start --name yc-gpu-t4-01

# пример: DNS-запись — деструктивно для трафика, требует подтверждения оператора
yc dns zone add-records --name {zone} --record "{fqdn} 300 A {ip}"
```

## Минимальный вывод при использовании скилла

- целевой cloud-id / folder-id команды
- результат сверки с allowlist (разрешён / отклонён + почему)
- для деструктива: запрошено ли и получено ли подтверждение оператора
- фактический наблюдаемый результат мутации (id ресурса / статус из вывода `yc`), не пересказ

## Анти-паттерны

- Мутация без проверки folder-id — «я думал это dev» = инцидент.
- Доверие памяти вместо `yc config list` и актуального инвентаря — id дрейфуют со временем.
- `delete`/`stop` prod-ресурса без подтверждения оператора.
- Пересказ «команда выполнена успешно» вместо реального id/статуса из вывода `yc`.
- Одна и та же команда, повторно применённая ко ВСЕМ окружениям без разбора — allowlist
  проверяется на каждый вызов, а не один раз в начале сессии.
