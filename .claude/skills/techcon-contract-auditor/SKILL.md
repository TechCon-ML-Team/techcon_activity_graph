# Аудитор межсервисных контрактов

Используй для обнаружения нетривиальных рассинхронов между сервисами
экосистемы TechCon, которые не видны из одного репозитория.

## Когда применять

- Аудит интеграции двух и более сервисов (один вызывает другой по HTTP,
  либо оба читают/пишут общую очередь).
- Подозрение на несовместимость: разные форматы ответа, разные имена
  очередей у producer и consumer, health-check не совпадает с тем, что
  реально проверяет мониторинг.
- Перед объединением или рефакторингом общего протокола между сервисами.

**Не применяется** к одиночному сервису без внешних интеграций — там
нечего сверять.

## Что проверять

### 1. Polling-роуты между сервисами

Если один сервис опрашивает другой по task-id, сверь:
- URL pattern (`/api/v1/task/{id}` vs `/result/{id}` vs `/status/{task_id}`
  — разные паттерны для одной и той же операции — рассинхрон);
- модель ответа (поля, типы, обязательность) — сравнить Pydantic/schema
  классы или `/openapi.json` обеих сторон.

```bash
# Прочитать openapi или схемы роутов у каждого сервиса
grep -rn "class.*Response\|@router\.\(get\|post\)" <repo>/**/routes/ 2>/dev/null
curl -s <service_url>/openapi.json | jq '.paths'
```

### 2. Envelope ответа (общий формат JSON)

Если экосистема или конкретная пара сервисов договорились об общем
формате (например `{"ok": bool, "data": ..., "error": null | {...}}`),
проверь:
- у каждого FastAPI/HTTP-сервиса — есть ли middleware/dependency,
  принудительно оборачивающий ответ в этот формат;
- нет ли эндпоинтов, отдающих «голый» JSON, HTML или файл там, где
  ожидается envelope (это не всегда баг — веб-страницы и экспорт файлов
  законно не оборачиваются, но зафиксируй как явное исключение, не как
  молчаливое расхождение).

```bash
grep -rn "class.*Response(BaseModel)\|ok.*bool\|middleware" <repo>/ 2>/dev/null | grep -v __pycache__
```

### 3. Коды ошибок

Проверь единообразие между сервисами:
- формат `detail`/`error` в `HTTPException` — одна и та же структура
  (`{"code": "SNAKE_CASE", "message": "..."}`) или у каждого сервиса своя;
- нет ли кастомных кодов ошибок, известных только одному сервису, хотя
  вызывающая сторона их не различает.

```bash
grep -rn "HTTPException\|raise.*Error" <repo>/ 2>/dev/null | grep -v __pycache__
```

### 4. Имена очередей/стримов между producer и consumer

Классический источник тихой поломки: сервис A пишет в очередь `X`, сервис
B слушает очередь `Y`, оба считают, что интеграция работает, пока не
проверишь явно.

```bash
# Найти реальные имена stream/queue/topic на стороне producer и consumer
grep -rn "xadd\|publish\|enqueue\|XREAD\|consumer_group\|topic=" <repo_producer>/ <repo_consumer>/ 2>/dev/null | grep -v __pycache__
```

Если имена не совпадают буквально — это либо незавершённая миграция, либо
два параллельных протокола. Не чини сам: зафиксируй находку и уточни у
владельца сервиса, какой контур канонический, прежде чем менять код.

### 5. Аутентификация между сервисами

- Есть ли флаг вида `DISABLE_AUTH`/`SKIP_AUTH`, и не остаётся ли он
  включённым в прод-конфигурации (сравнить dev/prod compose или env-файлы);
- fail-open vs fail-closed: если токен/секрет не задан в окружении,
  падает ли сервис в 401/403 или молча пропускает запрос;
- не передаётся ли токен через query-параметр (`?token=...`) — попадает в
  логи, историю браузера и `Referer`; корректно — только заголовок
  `Authorization: Bearer`.

```bash
grep -rn "DISABLE_AUTH\|SKIP_AUTH\|bypass\|bearer\|query_params.*token" <repo>/ 2>/dev/null | grep -v __pycache__
```

### 6. `/health` vs то, что реально проверяет мониторинг

Сравни, что ожидает watchdog/пробa мониторинга (формат JSON, поля,
ожидаемый статус-код) с тем, что реально возвращает эндпоинт `/health`
или `/healthz` сервиса. Расхождение даёт ложные срабатывания или, хуже,
тишину при реальном отказе.

```bash
grep -A5 "check\|health\|status" <monitoring_repo>/watchdog* 2>/dev/null
grep -A10 "def health\|/health\|/healthz" <service_repo>/**/main.py 2>/dev/null
```

### 7. Общий middleware

Есть ли переиспользуемый пакет middleware (envelope, error mapping,
rate-limit, CORS) между сервисами, или каждый реализует независимо? Если
независимо — рассинхрон п.2–3 будет повторяться при каждом новом сервисе.

## Формат вывода

```yaml
contract_audit:
  timestamp: "ISO-8601"
  severity_counts:
    critical: N
    high: N
    medium: N
  findings:
    - id: "<slug-находки>"
      severity: critical | high | medium
      services: ["<service_a>", "<service_b>"]
      description: "Что именно разошлось"
      files:
        - "<service_a>/path/to/file.py"
        - "<service_b>/path/to/file.py"
      recommendation: "Что сделать (зафиксировать канон, привести к общему виду)"
```

## Как фиксировать закрытые находки

При повторном аудите, если находка из прошлого отчёта устранена — не
удаляй её, добавь поле статуса:

```yaml
- id: "<slug-находки>"
  severity: critical
  status: "resolved"
  resolved_by: "<git SHA или краткое описание фикса>"
  verified: "<ISO-8601>"
```

Никогда не удаляй старые findings — это создаёт историческую запись.

## Правила работы

- Читать только исходники, не исполнять и не изменять код сервисов.
- Приоритизация: critical > high > medium.
  - critical = ломает интеграцию прямо сейчас или является риском
    безопасности в проде;
  - high = ломает при следующем изменении смежного сервиса, или высокий
    security risk без немедленного эффекта;
  - medium = техдолг, но работает сейчас.
- При каждом аудите верифицируй командами (grep/curl/openapi), не полагайся
  на данные из прошлого отчёта без перепроверки.
- Если контракт неоднозначен (два параллельных протокола, неясно какой
  канонический) — не чини сам, зафиксируй находку и предложи уточнить у
  владельца сервиса.
