# Инфраструктурный доступ TechCon

Используй этот скилл в любом репозитории организации, когда задача требует
доступа к VM-флоту, GitHub, GitLab, YC CLI или Linear — чтобы знать, что
можно делать без подтверждения оператора, а что нет.

## Источник истины — не память, а файл + живая команда

Инфраструктура организации меняется (машины гасятся, пересобираются, IP
переезжают). Любой адрес или id, вспомненный «из головы» или взятый из
старого документа/чата, с высокой вероятностью указывает на уже выведенный
ресурс. Прежде чем действовать:

1. Найди в проекте (или в его инфраструктурном репозитории-хранителе)
   machine-readable инвентарь флота — обычно `INFRA.yaml` или эквивалент:
   IP/алиасы, роли, статусы VM, cloud-id/folder-id.
2. Сверь его с живым замером, а не поверь ему на слово:
   ```bash
   yc compute instance list
   yc compute instance get --name {name}
   ```
   Документ описывает намерение и последнюю сверку; вопрос «что сейчас» —
   отдельный от вопроса «что записано».
3. Если такого файла в проекте нет вовсе — сначала найди источник истины
   (спроси оператора или поищи в связанных репозиториях организации), не
   восстанавливай данные по памяти.

Обращайся к хостам по алиасу из инвентаря/`~/.ssh/config`, не по IP-адресу:
алиас переживает замену машины, адрес — нет.

## 1. SSH / VM

```bash
# Живые хосты — брать из инвентаря флота, не из памяти/старого чата
ssh {alias}                       # прямой вход / бастион, если публичный
ssh -J {bastion-alias} {vm-alias} # внутренние узлы — только через бастион

# Ключи — стабильные ИМЕНА файлов, содержимое может быть ротировано;
# конкретные имена берутся из инвентаря доступов проекта
```

### Read-only / operator-gated

```bash
# РАЗРЕШЕНО без подтверждения (read-only диагностика)
yc compute instance list
yc compute instance get --name {name}
ssh {alias} 'systemctl status {service}'
ssh {alias} 'docker ps'
ssh {alias} 'tail -50 /var/log/{logfile}'

# ТРЕБУЕТ явного подтверждения оператора (мутация)
yc compute instance start --name {name}
yc compute instance stop --name {name}
yc compute instance reboot --name {name}
ssh {alias} 'systemctl restart {service}'
```

## 2. GitHub

```bash
gh auth status                 # проверить авторизацию
gh auth login                  # один раз, если не авторизован

gh pr list --repo {org}/{repo}
gh run list --repo {org}/{repo} --limit 5
gh issue create --repo {org}/{repo} --title "..." --body "..."
gh api repos/{org}/{repo}/commits --jq '.[0].sha'
```

## 3. GitLab (если подключён — обычно read-only)

Если у проекта есть GitLab-интеграция, по умолчанию считай её read-only,
пока явно не сказано иное — запись в чужой GitLab-инстанс без явного
мандата создаёт риск, которого легко избежать.

```bash
# Проверить, что токен доступа установлен (без вывода значения)
echo ${GITLAB_TOKEN:0:0} >/dev/null && [ -n "$GITLAB_TOKEN" ] && echo set
```

## 4. YC CLI

```bash
yc config list                          # текущий профиль: cloud-id, folder-id

# Read-only — безопасно
yc compute instance list
yc managed-redis cluster list
yc container registry list

# Логи, если доступно
yc logging read --folder-id {folder-id} --since 1h
```

Мутирующие команды (`create`/`update`/`delete`/`start`/`stop`) — только
после сверки cloud-id/folder-id с allowlist инвентаря и, для деструктива,
после явного подтверждения оператора.

## 5. Linear (задачи и проекты)

```bash
# Проверить, что API-ключ установлен (без вывода значения)
[ -n "$LINEAR_API_KEY" ] && echo set
```

Без ключа доступ обычно идёт через OAuth при первом вызове инструмента.
Перед созданием/правкой задач сверься с принятыми в организации правилами
описания задач и транспорта (команда, проекты, лейблы, приоритеты) — они
обычно живут отдельными стандартами в инфраструктурном репозитории.

## 6. Протокол `TECHCON_ACCESS.md` в репозитории

Каждый репозиторий организации может держать у себя `TECHCON_ACCESS.md` —
локальное зеркало инфра-договора без секретов, чтобы агент, открывший
именно этот репозиторий, не искал доступы по всей организации.

### Когда обновлять

1. Меняются IP или SSH-алиасы VM.
2. Добавляются или удаляются VM.
3. Меняются правила безопасности (что read-only, что operator-gated).
4. Ротируются ключи (меняются стабильные имена файлов ключей).

Правки вносятся через PR в целевой репозиторий, не прямым push и не
файловым обменом в обход обычного git-потока.

### Шаблон `TECHCON_ACCESS.md`

```markdown
# TechCon — памятка по доступу без секретов

## Канонический источник
Инвентарь VM-флота и SSH-справочник организации — см. инфраструктурный
репозиторий-хранитель (актуальный путь спросить у оператора при первом
использовании, не угадывать).

## Режимы доступа
- ssh-direct — список хостов с прямым входом
- ssh-internal-via-bastion — внутренние подсети через конкретный бастион
- yc-cli-first — read-only инвентарь свободно, mutation — с одобрением оператора

## Стабильные имена ключей
- основной: ~/.ssh/{имя}
- резервный: ~/.ssh/{имя}

## GitHub
- Доступ через gh CLI (`gh auth login` выполнен)
- Org/repo — согласно проекту

## GitLab (если подключён)
- Токен через переменную окружения, scope read_api/read_repository
- Запись — только если явно разрешена

## Правила безопасности
- read-only YC диагностика — без подтверждения
- SSH-мутация (restart и т.п.) — без явного разрешения в задаче запрещена
- start/stop/reboot VM — всегда operator-gated
- Не хранить ключи, токены, VPN-конфиги в git
```

## Красные флаги (остановиться и проверить)

- VM недоступна по SSH — сначала `yc compute instance list`, потом эскалация.
- GitLab/GitHub отдаёт 401/403 — токен истёк или не хватает scope,
  переавторизоваться, не подбирать альтернативные креды.
- Переменная с токеном не установлена — соответствующий инструмент
  недоступен, задачи, требующие его, — стоп, а не обход через угаданные
  значения.
- IP/алиас в инвентаре расходится с живым замером — обновить инвентарь
  через PR, не работать по памяти дальше.
