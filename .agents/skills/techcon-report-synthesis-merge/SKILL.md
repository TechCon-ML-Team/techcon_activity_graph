# Синтез сводного отчёта из нескольких готовых кейсов

Портируемая директива, не программа. Читается и исполняется любым агентным
harness'ом построчно — обычными командами оболочки и чтением файлов, без
вызовов, специфичных для конкретного инструмента. Применимо к отчётам
любого репозитория TechCon: инфраструктурным сводкам, дашбордам прогресса,
презентациям для руководства.

## Goal

Собрать N уже одобренных отдельных кейсов/дашбордов в ОДИН документ для
одной аудитории (обычно руководство), сохранив глубину и точность каждого
источника, но добавив связующий нарратив, который объясняет, почему они
показаны вместе, и убирает дублирование формата (не контента).

## Когда это применимо

- Несколько отчётов по РАЗНЫМ, но тематически связанным проектам (пример:
  инфраструктура + мониторинг флота — общий вычислительный фундамент
  экосистемы).
- Один отчёт по ОДНОМУ проекту, повторённый за несколько периодов
  (еженедельные срезы), которые нужно свести в единую презентацию
  динамики за более долгий срок.
- **НЕ применимо**: объединение тематически не связанных кейсов только
  ради «одного файла» — если общая рамка не формулируется одним
  предложением, это неправильный кандидат на синтез (см. Anti-patterns).

## Фаза 0 — Отбор источников (ОБЯЗАТЕЛЬНА)

1. Каждый источник ДОЛЖЕН уже быть отдельно написан и проверен (баланс
   тегов, латиница/кириллица не вперемешку, отсутствие неопределённых
   CSS-классов, отсутствие неподтверждённых чисел) и, если применимо,
   одобрен человеком. Синтез не чинит и не улучшает контент источника — он
   его комбинирует. Если источник сам содержит непроверенные CSS-классы
   или недостоверные числа — это чинится В ИСТОЧНИКЕ, отдельным шагом, ДО
   синтеза (живой прецедент: два CSS-класса использовались в разметке
   одного источника, но нигде не были определены в его `<style>` — найдено
   и исправлено отдельным коммитом прежде, чем эта секция попала в сводный
   документ).
2. Явно зафиксировать: какова ОБЩАЯ РАМКА, объединяющая источники (одна
   экосистема? один период? одна тема?). Без явной рамки связующий
   нарратив выйдет генерическим клеем — «зачем это нужно» получится
   пустой фразой.
3. Проверить пересечение чисел между источниками. Если один и тот же факт
   встречается в двух источниках с разными значениями (разные даты
   замера) — явно взять более свежее и не молчать про расхождение, тот же
   принцип, что уже применяется к живым числам одного проекта.

## Фаза 1 — Извлечение общего визуального языка

1. Прочитать `<style>`-блок(и) каждого источника, выписать ВСЕ локальные
   (не входящие в общий design kit) классы и их определения.
2. Объединить в ОДИН `<style>`-блок для сводного документа — дедуплицировать
   одинаковые определения, при расхождении взять более свежую/полную
   версию.
3. Проверить результат слияния: каждый класс, использованный в разметке,
   реально определён. Слияние `<style>`-блоков — частая точка появления
   НОВЫХ багов этого класса: легко забыть скопировать один локальный класс
   из трёх источников, хотя в каждом источнике по отдельности всё было
   исправно.

## Фаза 2 — Связующий нарратив (не механическая конкатенация)

Синтез — это не «взять N файлов и склеить». Обязательные добавленные
элементы:

1. **Общий hero**, отражающий объединённую рамку — не hero одного из
   источников и не два hero подряд (пример: «Инфраструктура и мониторинг
   экосистемы» одним заголовком и одним набором бейджей, не
   «Инфраструктура» + отдельно «Мониторинг»).
2. **Секция «зачем это нужно / зачем показаны вместе»** — явно объясняет
   читателю связь между источниками до того, как он увидит первую
   предметную секцию.
3. **Сквозные темы (опоры/пиллары)**, если у источников есть похожие
   структурные единицы. Не дублировать их как две независимые группы без
   объяснения — либо явно пронумеровать сквозным счётом (например 01–06
   на шесть опор из двух источников по три), либо явно подписать, к
   какому источнику относится каждая группа.
4. **Визуальные разделители по источнику** — простой, ненавязчивый маркер
   (тонкая линия с подписью вроде «Проект А» / «Проект Б» / «Общее
   направление») в точках, где нарратив переходит от одного источника к
   другому. Читатель не должен терять, о каком проекте сейчас речь.
5. **Итоговый объединённый роадмап** — не два независимых списка «куда
   дальше» друг под другом без связи, а явно сгруппированные по источнику
   (или по теме, если источники близки) блоки в одной секции.

## Фаза 3 — Перенос секций

1. Секции с высокой предметной ценностью (таймлайны, диаграммы экономики,
   топологии, incident-grid, плотные хронологические ленты) переносятся ИЗ
   ИСТОЧНИКА ДОСЛОВНО — не переписываются заново. Синтез уважает уже
   проделанную и одобренную работу, а не производит её заново.
2. Если один и тот же ТИП контента (например «как мы ловим сбои») есть в
   обоих источниках, но с разной допустимой степенью конкретики (пример:
   один источник показывает именованные инциденты с датами, другой —
   только агрегированную безымянную статистику, не конкретные случаи, по
   прямому решению владельца) — сохранить эту разницу в стиле подачи.
   Источник сам определяет, насколько конкретен он может быть о своих
   находках; синтез не приводит оба к одному уровню детализации
   искусственно.
3. **Не переносить специфику одного проекта в раздел другого.** Если
   источник в своё время уже исправил жалобу вида «зачем сюда подтягиваются
   инциденты чужого проекта» — синтез не должен реинтродуцировать ту же
   ошибку, комбинируя источники: инциденты проекта Б остаются в секции Б,
   инциденты проекта А — в секции А. Единственное место, где содержание
   источников сознательно смешивается, — специально спроектированная
   сквозная секция уровня «Общее направление» (см. Фаза 2, пп. 3–4), и то
   по темам (общие принципы, общий роадмап), не по фактам одного проекта,
   выданным за факты другого.

## Working rules

- Объём: сводный документ закономерно больше суммы источников по глубине
  подачи (связующие секции, дедупликация формата, а не сжатие контента) —
  2–3× по отношению к ОДНОМУ источнику ожидаемо и не является перегрузом,
  если каждая добавленная секция несёт информацию, а не воду. Не сокращать
  источники ради «более короткого» результата, если явно не попросили
  обратное.
- Место назначения синтеза определяет человек (например конкретная папка
  для презентации руководству). Если он явно попросит зарегистрировать
  синтез как отслеживаемый канонический документ проекта — это отдельное
  явное решение, не действие по умолчанию.
- Применимо и к «еженедельным дашбордам»: тот же рецепт работает, если
  источники — это не N разных проектов, а один и тот же формат кейса,
  повторённый по N периодам (например по неделям), которые нужно свести в
  одну презентацию прогресса. Общая рамка тогда — «прогресс за период»,
  связующий нарратив явно показывает динамику между срезами (что
  изменилось от среза к срезу), а не просто ставит их друг под другом по
  порядку.

## Minimum output

- Один HTML-файл, тег-баланс сходится, единый `<style>`-блок без
  дублирующихся определений и без неопределённых классов.
- Явная связующая рамка в интро (не «просто N кейсов рядом»).
- Визуальные маркеры перехода между источниками.
- Единый объединённый роадмап.
- Итоговая проверка (баланс тегов, латиница/кириллица вперемешку,
  неопределённые CSS-классы, неподтверждённые числа) применена к финальному
  файлу целиком, не только к добавленным секциям.

## Anti-patterns

- Механическая конкатенация без нового hero/интро/пилларов — читается как
  «файл А плюс файл Б», не как единый документ.
- Искусственное сокращение источников ради компактности, когда пользователь
  явно разрешил больший объём.
- Смешение конкретики одного источника в раздел другого без явного
  намерения (см. Фаза 3, п. 3) — особенно опасно, если один из источников
  уже прошёл правку именно против такого смешения.
- Забытый локальный CSS-класс при объединении `<style>`-блоков — самый
  частый новый баг именно в синтезе; проверять отдельно после сборки, не
  полагаться на то, что каждый источник уже был чист по отдельности.
- Синтез тематически не связанных кейсов только ради «одного файла» — если
  рамка не объясняется одним предложением, это неправильный кандидат на
  синтез.
