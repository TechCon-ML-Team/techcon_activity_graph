# Research-First — исследовательский проход перед реализацией

Перед крупной задачей, архитектурным решением или значительным изменением сначала
собери факты и зафиксируй риски — и только потом переходи к реализации. Задача без
этого прохода не считается готовой к реализации.

## Когда применять

- Новая фича или компонент (>50 строк изменений)
- Архитектурное решение с долгосрочными последствиями
- Интеграция с внешней системой или библиотекой
- Рефакторинг, затрагивающий >2 файлов
- Любая задача, где нет уверенности в implementation-ready состоянии

## Процесс (в этом порядке)

### Шаг 1: Контекст репозитория

```
read  файлы с правилами/архитектурой репозитория (README, AGENTS.md, CONTRIBUTING.md
      или аналог — то, что репозиторий сам называет источником правды)
read  причастные исходные файлы           → текущее состояние кода
run   git log --oneline -10 -- <область>  → история изменений в области
```

### Шаг 2: Внешний контекст

- Официальная документация relevant subsystems и зависимостей
- Known issues, breaking changes, community best practices
- Аналогичные реализации в этой же кодовой базе (grep по паттерну)
- Известные workarounds для проблем, если они уже встречались раньше

### Шаг 3: Фиксация результата

Перед началом кода зафиксировать компактно:

```
ФАКТЫ:
- [что подтверждено источниками]

РИСКИ:
- [что может сломаться или усложниться]

УДАЛИТЬ/ИЗБЕЖАТЬ:
- [анти-паттерны, устаревшие подходы, известные ловушки]

ОТКРЫТЫЕ ВОПРОСЫ:
- [что ещё нужно прояснить перед реализацией]
```

## Правила

- Research-first и тесты (TDD) равносильны по строгости — задача не готова, если
  выполнено только одно из двух.
- Для архитектурных решений обязателен критический проход: факты → черновик →
  критика черновика → ревью интеграции → декомпозиция на шаги.
- Если research-first был пропущен или выполнен постфактум — это стоит явно
  отметить в отчёте о задаче, а не скрывать.
- Если шаги 1 и 2 можно было выполнить параллельно, но выполнены линейно — тоже
  стоит отметить: это потерянное время на следующей похожей задаче.

## Output contract

После research-first возвращать:
- `facts` — подтверждённые наблюдения с источниками (файл/команда/URL)
- `risks` — риски, ранжированные по вероятности × последствиям
- `ready` — `yes` | `blocked` (если `blocked` — что именно блокирует)
