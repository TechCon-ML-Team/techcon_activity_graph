# Харнесс агентов TechCon — полный справочник

Этот файл раздаётся в каждый репозиторий `techcon_*` как `.agents/REFERENCE.md`. Он
самодостаточен: всё, что нужно знать о командах, правилах и настройке харнесса, — здесь.
Если вы только начинаете — сначала `.agents/GETTING-STARTED.md` в этом же репозитории,
там простыми словами объяснено, что это и как поставить. Этот документ — для тех, кто
уже поставил харнесс и хочет знать, что именно он делает и как его настроить: людей,
которые администрируют репозиторий, и ИИ-помощников, которым нужны точные команды.

## Содержание

1. Все подкоманды CLI
2. Хуки и правила — реестр, три слоя настройки
3. `hook disable-all`
4. Локальные, нераспространяемые скиллы репозитория
5. Кастомизация — профили автономности
6. Полный каталог дополнений
7. Формат коммитов
8. macOS — что не проверено

## 1. Все подкоманды CLI

Вызов сегодня: `python3 -m cli.techcon_harness <подкоманда> [...]`. Отдельного
исполняемого файла `techcon-harness` пока нет — он появится вместе с установщиком.
Каждая подкоманда возвращает один из трёх кодов выхода: `0` — норма, `1` — нарушение
или отказ по правилу, `2` — не измерено (нельзя ответить на вопрос, не то же самое,
что «всё в порядке»).

### `doctor`

Самопроверка репозитория: генерация = коммит, реестр правил согласован, схемы
синхронны. Печатает таблицу «правило, источник, режим».

```bash
python3 -m cli.techcon_harness doctor
python3 -m cli.techcon_harness doctor --repo-root <путь>   # по умолчанию — текущий каталог
python3 -m cli.techcon_harness doctor --machine             # см. ниже
```

`--machine` — отдельный вопрос: развёрнут ли машинный слой на **этой машине** (только
локальные файлы: `/opt/techcon-harness/hooks/run.py`, `~/.claude/settings.json`,
`/etc/codex/requirements.toml`). Ничего из репозитория не исполняется. Коды выхода:
`0` — развёрнуто, `1` — не развёрнуто.

### `hook`

Управление правилами хуков — подробно в разделе 2 ниже.

```bash
python3 -m cli.techcon_harness hook list
python3 -m cli.techcon_harness hook disable <id> --reason ТЕКСТ [--until YYYY-MM-DD] [--false-positive true|false]
python3 -m cli.techcon_harness hook enable <id>
python3 -m cli.techcon_harness hook mode <id> <observe|enforce>
python3 -m cli.techcon_harness hook disable-all --reason ТЕКСТ --until YYYY-MM-DD
```

### `profile`

Профиль автономности — см. раздел 5.

```bash
python3 -m cli.techcon_harness profile show
python3 -m cli.techcon_harness profile set strict|standard|autonomous
```

### `pin`

Закреплённая версия харнесса на машине. Хранится локально
(`~/.local/state/techcon-harness/pin.json`), в сеть ничего не отправляется.

```bash
python3 -m cli.techcon_harness pin show
python3 -m cli.techcon_harness pin set <sha-40-hex|канал>
python3 -m cli.techcon_harness pin rollback   # вернуть предыдущий пин
```

### `addons`

Разбор каталога дополнений и их установка — читает `docs/recommended-addons.md`
харнесса.

```bash
python3 -m cli.techcon_harness addons list
python3 -m cli.techcon_harness addons list --harness claude   # только для Claude Code
python3 -m cli.techcon_harness addons list --json
python3 -m cli.techcon_harness addons install <name> --dry-run
python3 -m cli.techcon_harness addons install <name> --yes
```

Без `--yes` `install` только печатает план и не меняет систему. Устанавливать можно
только запись каталога с явно закреплённой командой (строка «Установка (pin):» в
каталоге); разрешены только исполнители из allowlist (`npx`, `npm`, `uvx`, `uv`, `pip`,
`pipx`, `cargo`) — подстановки команд, пайпы, `curl`/`wget`, `sh`/`bash`, `sudo`
запрещены безусловно.

### `report`

Локальный журнал сессий — не сеть, только файлы на машине.

```bash
python3 -m cli.techcon_harness report session                 # что произошло в конце последней сессии
python3 -m cli.techcon_harness report week                    # то же за 7 дней, по репозиториям
python3 -m cli.techcon_harness report run --since <ISO 8601> [--until <ISO 8601>] [--repo <путь>]
python3 -m cli.techcon_harness report session --false-positives  # доля ложных срабатываний правил
python3 -m cli.techcon_harness report <scope> --json           # машинный вывод
python3 -m cli.techcon_harness report <scope> --strict          # код 2, если измерены не все поля
```

### `telemetry`

Переключает ключи телеметрии (только метрики: стоимость, токены, число сессий —
содержимое промптов и команд не отправляется никогда) в явно указанном
`settings.json`.

```bash
python3 -m cli.techcon_harness telemetry status --settings ~/.claude/settings.json
python3 -m cli.techcon_harness telemetry on --settings ~/.claude/settings.json --apply
python3 -m cli.techcon_harness telemetry off --settings ~/.claude/settings.json --apply
```

Без `--apply` — только показывает, что изменится (сухой прогон); значения переменных
(адрес приёма, заголовки, ключи доступа) никогда не печатаются, только имена ключей.

### `skill`

Работа со скиллами.

```bash
python3 -m cli.techcon_harness skill lint skills/techcon-<slug>   # проверка формата
python3 -m cli.techcon_harness skill new <name>                   # каркас нового скилла
python3 -m cli.techcon_harness skill eval techcon-<slug>           # живой прогон судьи (haiku)
```

### `tests-coverage` и `standards-coverage`

```bash
python3 -m cli.techcon_harness tests-coverage    # правило «код без tests/» — присутствие, не построчное покрытие
python3 -m cli.techcon_harness standards-coverage   # сверяет standards/matrix.yaml с реальными модулями
```

### `commit-lint`

Проверка формата сообщения коммита на Conventional Commits. Подробно — раздел 7.

```bash
python3 -m cli.techcon_harness commit-lint <путь-к-файлу-сообщения>   # контракт git commit-msg хука
python3 -m cli.techcon_harness commit-lint --message "fix(hooks): пример"
python3 -m cli.techcon_harness commit-lint --range origin/develop..HEAD   # весь диапазон разом, для CI
```

### `pii-scan`

Наблюдательная проверка (режим `observe`, не блокирует) на явные формы персональных
данных в переданных путях.

```bash
python3 -m cli.techcon_harness pii-scan --paths <файл-или-каталог> [<ещё> ...]
```

### `linear-lint`

Проверка формата трейлера `Linear: TML-<id>` в теле коммита (тем же механизмом, что
`commit-lint` — git `commit-msg` хук).

```bash
python3 -m cli.techcon_harness linear-lint <путь-к-файлу-сообщения>
python3 -m cli.techcon_harness linear-lint --message "..."
```

Трейлер нужен не каждому коммиту — только тем, что продвигают содержательную работу.
Отсутствие трейлера у служебного коммита не нарушение.

## 2. Хуки и правила

Хук — короткая программа, которая запускается до или после действия помощника.
Опасное действие она запрещает (`enforce`, режим доставки `block`), про упущенное —
советует (`observe`, режим доставки `additionalContext`, помощник видит совет прямо в
контексте сессии).

### Реестр правил

Источник правды — `hooks/registry_seed.json` в `techcon_agent_harness`. На момент
раздачи этой копии в реестре 10 правил:

| id | класс | режим по умолчанию | можно отключить | команда отключения |
|---|---|---|---|---|
| `gh-pr-merge-admin` | 1 | enforce (запрет) | да, с причиной и сроком | `hook disable gh-pr-merge-admin --reason "..." --until YYYY-MM-DD` |
| `force-push-protected` | 1 | enforce (запрет) | да, с причиной и сроком | `hook disable force-push-protected --reason "..." --until YYYY-MM-DD` |
| `yc-lockbox-payload-unfiltered` | 1 | enforce (запрет) | да, с причиной и сроком | `hook disable yc-lockbox-payload-unfiltered --reason "..." --until YYYY-MM-DD` |
| `edit-machine-layer-config` | 1 | enforce (запрет) | да, с причиной и сроком | `hook disable edit-machine-layer-config --reason "..." --until YYYY-MM-DD` |
| `tests-coverage-stop` | 2 | observe (совет) | да, свободно | `hook disable tests-coverage-stop` |
| `session-journal-stop` | 2 | observe (совет) | да, свободно | `hook disable session-journal-stop` |
| `code-format-check` | 2 | observe (совет) | да, свободно | `hook disable code-format-check` |
| `language-check` | 2 | observe (совет) | да, свободно | `hook disable language-check` |
| `api-docs-check` | 2 | observe (совет) | да, свободно | `hook disable api-docs-check` |
| `brand-tokens-check` | 2 | observe (совет) | да, свободно | `hook disable brand-tokens-check` |

Класс 1 — защита от опасного (обход защиты веток, принудительная перезапись общей
истории, вывод ключа доступа целиком, правка самого слоя настроек хука): отключение
требует `--reason` (обязательно, без исключений) и `--until` в формате `YYYY-MM-DD`
(по умолчанию — 30 суток от сегодня, дальше правило включается само; дальше 90 суток
от сегодня команда отклоняет запрос). Класс 2 — стандарты и напоминания: отключение
свободное, без причины и срока.

Точный список правил и режимы для вашей копии репозитория — живая команда, не эта
таблица (таблица описывает состояние на момент, когда писался этот файл):

```bash
python3 -m cli.techcon_harness hook list
```

### Три слоя настройки

Хук смотрит на три слоя, от жёсткого к мягкому:

| слой | где лежит | что может |
|---|---|---|
| **код** | `hooks/registry_seed.json` харнесса | базовый режим правила; меняется только выпуском харнесса |
| **личный** | `~/.config/techcon-harness/hooks.yaml` на вашей машине | отключить **любое** правило, включая класс 1 — но только из терминала человеком, с причиной и сроком (для класса 1) |
| **репозитория** | `.agents/harness.local.yaml` в общем клоне | только **ужесточать** (`observe` → `enforce`); ключ отключения в нём игнорируется и показывается как «отклонено» |

Причина асимметрии: личный файл видит только его владелец, а файл репозитория
коммитится и виден всем, кто клонирует репозиторий, — если бы он мог отключать, один
запрос на слияние выключил бы защиту сразу всем, кто работает с репозиторием.

Все три слоя (включая `~/.claude/settings*.json`, `.claude/settings*.json` в проекте,
`/opt/techcon-harness`, `/etc/codex`, `.codex/` в проекте) защищены отдельным правилом
класса 1 — `edit-machine-layer-config`: запись или изменение любого из этих путей
другим инструментом (не через команду `hook`) запрещены по умолчанию, иначе
самоотключение защиты одной правкой файла обошло бы весь класс 1 сразу.

**Безопасный отказ.** Любая ошибка личного или репо-файла (симлинк, файл не текущего
пользователя, права шире `0600` для личного файла, файл больше лимита, невалидный
YAML, неизвестные ключи, испорченный или просроченный срок отключения) не приводит к
падению — либо файл целиком игнорируется (эффективный режим — режим по умолчанию из
реестра, то есть `enforce` для класса 1), либо отбрасывается только проблемная запись.
Оба случая попадают в предупреждения `doctor`/журнала — тихого провала нет.

Режим нельзя задать переменной окружения — только содержимым файлов на указанных
путях.

## 3. `hook disable-all`

Массовое отключение всех правил разом (эргономика поверх `hook disable`, не отдельный
механизм) — оба флага обязательны без исключений:

```bash
python3 -m cli.techcon_harness hook disable-all --reason "разбираюсь с ложными срабатываниями во всём наборе" --until 2026-10-15
```

Команда проходит по всем правилам реестра и записывает отключение в личный слой
(`~/.config/techcon-harness/hooks.yaml`) для каждого — то же место, что и обычный
`hook disable`, не отдельный ad-hoc путь. Как и одиночный `disable`, требует
интерактивный терминал (только человек может ослаблять защиту) — при непосредственном
вызове не из терминала команда отказывает. `--until` дальше `90` суток от сегодня
отклоняется. Обратная команда — `hook enable <id>` для каждого правила по отдельности,
других способов включить всё разом не предусмотрено намеренно: массовое включение не
несёт того же риска, что массовое отключение, и не нуждается в отдельной команде.

**Известный остаточный риск (принят, задокументирован в `docs/threat-model.md` R-H):**
запись отключения идёт по одному правилу за раз, не единой транзакцией — если процесс
прервать (`Ctrl-C`, потеря питания) посреди `disable-all`, часть правил останется
отключённой без явного следа, что это была именно прерванная массовая команда, а не
несколько осознанных точечных `disable`. `doctor`/`hook list` в любом случае покажут
фактическое состояние реестра после любой мутации — проверяйте им, если подозреваете
прерывание. Отдельно: `disable-all` безусловно перезаписывает `reason`/`until` даже у
правил, уже отключённых индивидуально ранее с более специфичной причиной — старая запись
молча заменяется (ожидаемое поведение массового действия, не угроза безопасности).

## 4. Локальные, нераспространяемые скиллы репозитория

Не каждый скилл, написанный для конкретного репозитория, имеет смысл раздавать всей
организации (специфичный для сервиса чек-лист, разовая интеграция, личная заметка
коллеги). Для такого скилла — свой каталог в repo-слое, раздача харнесса его не
трогает и не удаляет:

```
.agents/skills/local/<имя-скилла>/SKILL.md
.claude/skills/local/<имя-скилла>/SKILL.md   # зеркало, если нужно и здесь
```

Формат `SKILL.md` — тот же, что у любого скилла (frontmatter + тело); поле `harness:`
не обязательно, но лучше явно поставить `harness: repo`, чтобы у любого, кто откроет
файл, не было вопроса «а это точно не раздача».

Почему именно `local/`, а не произвольное имя папки: компилятор раздачи
(`compiler/build_repo_release.py`) считает коллизией и «осиротевшим орг-скиллом» только
имена, совпадающие с реальными орг-скиллами харнесса, — сам по себе он не тронет ничего
с другим именем. Каталог `local/` — соглашение для людей: один явно названный каталог
проще внести в исключения будущих проверок расхождения, чем доказывать по каждому имени
папки, что оно «случайно не совпало» с будущим орг-скиллом.

Полное описание формата скилла, `evals/cases.yaml`, порядок продвижения репо-скилла в
орг-скилл — файл `docs/skill-authoring.md` в `techcon_agent_harness`, если у вас есть к
нему доступ; если нет — минимальный формат описан выше достаточен для локального
скилла, который никуда продвигать не планируется.

## 5. Кастомизация — профили автономности

Профиль хранится локально (`~/.local/state/techcon-harness/profile.json`), по умолчанию
`standard`.

```bash
python3 -m cli.techcon_harness profile show
python3 -m cli.techcon_harness profile set strict
python3 -m cli.techcon_harness profile set standard
python3 -m cli.techcon_harness profile set autonomous
```

Три профиля и их компромисс:

- **`strict`** — «все возможные правила enforce». Записывает **репо-слой**
  (`.agents/harness.local.yaml`) со значением `mode: enforce` для каждого класс-2
  правила. Подходит, когда вы хотите, чтобы советующие правила (язык, формат кода,
  API-документация, фирменные цвета) блокировали действие, а не только напоминали —
  например, перед приёмкой большого внешнего вклада. Класс 1 уже `enforce` по
  умолчанию, трогать нечего.
- **`standard`** (по умолчанию) — снимает repo-override, поставленные `strict`, по тем
  же ключам. Личные `hook disable` записи пользователя (сделанные явно, с причиной)
  этим профилем не трогаются ни в одну сторону — это ваш отдельный, осознанный выбор,
  а не то, что профиль должен молча стирать.
- **`autonomous`** — «observe кроме класса 1». Честно **ничего не меняет** в слоях
  настройки: класс 2 и так `observe` по умолчанию, а класс 1 не имеет режима `observe`
  вообще (отключается только целиком, через `hook disable`, с причиной и сроком) — этому
  профилю физически нечего переключать сверх уже действующего по умолчанию. `doctor`/
  `hook list` покажут такие правила с источником `default`. `set autonomous` разрешён
  только внутри `git worktree` (не в основном чекауте) — автономный режим не должен
  затрагивать общее рабочее дерево.

Если `set autonomous` вызван вне worktree, команда отказывает и подсказывает команду
создания: `git worktree add /tmp/wt-<задача> -b <ветка> origin/main`.

## 7. Формат коммитов

Заголовок коммита — Conventional Commits: `<type>(<scope>): <summary>`. Список типов
закрыт:

```
feat fix docs style refactor perf test build ci chore revert
```

Типа вне этого списка не существует — гейт `commit-lint` отклонит заголовок с
придуманным типом (например, несуществующим `alerts(...)`), а если такой коммит уже
отправлен на сервер, чинится только переписыванием истории, не последующим коммитом.
Мёрж-коммиты (`Merge pull request #N from ...`) исключены из проверки — так их создаёт
сам GitHub, не человек и не помощник.

Агентский коммит несёт трейлер `Co-Authored-By:` с указанием модели сессии. Один коммит
— одно логическое изменение, не смешивайте несвязанные правки в одном коммите.

Полная операционализация (кто и как выполняет слияние веток, обязательный возврат
хотфикса из `main` в `develop`, привязка коммита к задаче Linear трейлером
`Linear: TML-<id>`) — скилл `techcon-git-workflow` в этом репозитории, если он у вас
раздан: `.claude/skills/techcon-git-workflow/SKILL.md` или
`.agents/skills/techcon-git-workflow/SKILL.md`.

## 8. macOS — что не проверено

Установщик и раннер хуков написаны переносимо (`shutil`/`pathlib`, без вызовов,
специфичных для Linux), но живой запуск на реальном macOS ни разу не выполнялся — в
организации нет macOS-машины для этой проверки.

Что теоретически должно работать без изменений:
- проверка подписи выпуска (`ssh-keygen -Y`, если версия macOS достаточно новая —
  проверьте `ssh-keygen -Y 2>&1 | head -2`);
- слияние ключа `hooks` в `~/.claude/settings.json` тем же кодом, что на Linux;
- запуск самих хуков (`hooks/run.py`) — модуль не завязан на платформу.

Что отличается и не подтверждено:
- путь машинного слоя — `/Library/Application Support/ClaudeCode/` и
  `/private/etc/codex` вместо `/opt/techcon-harness` и `/etc/codex`; установщик их не
  проверял живьём;
- системный `python3` на свежем macOS может быть заглушкой Xcode без реального
  интерпретатора — поставьте Python 3.11+ через `brew` заранее;
- служба самопроверки (аналог systemd-таймера) на macOS через `launchd`, шаблоны —
  `local/macos/com.techcon-harness.*.plist` в `techcon_agent_harness`, если у вас есть к
  нему доступ; структурно провалидированы, живьём не запускались.

**Если вы ставите харнесс на macOS первым** — пройдите шаги из
`.agents/GETTING-STARTED.md` и зафиксируйте результат каждого пункта (сработало/нет) в
сообщении владельцу харнесса:

1. `python3 --version` ≥ 3.11; `ssh-keygen -Y` доступен.
2. `./installer/install.sh ...` **без** флага `--apply` (это и есть режим проверки —
   отдельного флага `--check` у скрипта нет) — код 0, подпись валидна.
3. `./installer/install.sh --apply ...` — какой фактический путь занял машинный слой.
4. Хук блокирует опасную команду (например, `gh pr merge --admin`) в вашей сессии.
5. `settings.json` после установки: ваши прежние ключи на месте.
6. `--uninstall` — машина возвращается в состояние до установки.

Любое расхождение с ожиданием выше — не повод останавливаться самостоятельно и
патчить установщик наугад: сообщите точную команду и вывод владельцу харнесса, откат
(`--uninstall` с теми же `--backup-root`/`--session-id`) безопасен в любой момент.
