# Шаблон архитектурных границ

## Когда применять

- При онбординге нового репозитория без существующего arch-lint конфига.
- По прямому запросу пользователя: «настрой проверку архитектурных границ», «запрети domain
  импортировать infra», «проверь граф зависимостей между модулями».

**Не применяется:**
- К репозиторию БЕЗ выраженной слоистой структуры (простой скрипт, монолитный `main.py`) —
  предлагать конфиг с пустым `forbidden`-списком создаёт cargo-cult файл без пользы.
- К репозиторию, где arch-lint конфиг уже существует (`.dependency-cruiser.cjs` / `.importlinter`
  / `.go-arch-lint.yml` / `scripts/check-crate-boundaries.sh`) — не предлагать замену, не
  автопатчить существующий файл.

## Процесс

1. **Детекция стека** — прочитай `package.json`/`pyproject.toml`/`go.mod`/`Cargo.toml` в корне
   репозитория, чтобы определить язык и пакетный менеджер.
2. **Детекция слоёв** — найди пары директорий по типовым DDD/hexagonal соглашениям:
   - `src/domain` + `src/infra` (TS/Python/Go)
   - `core/` + `adapters/`
   - `application/` + `infrastructure/`
   - `internal/domain` + `internal/infra` (Go)
   - Multi-crate workspace: `crates/*/Cargo.toml` с ≥2 крейтами (Rust)
3. **Если слои не найдены** — не предлагай ничего, не упоминай в итоговом отчёте (молчаливый
   skip, не «нашёл, но не подходит» — если триггера нет, skill не оставляет след в диалоге).
4. **Если слои найдены и конфиг не существует** — покажи предложение пользователю (формат ниже),
   жди `Y/n`.
5. **При подтверждении:**
   - Возьми соответствующий шаблон под язык проекта (`dependency-cruiser.config.cjs` для TS,
     `.importlinter` для Python, `go-arch-lint.yml` для Go, `check-crate-boundaries.sh` для Rust)
     — из внутренней библиотеки шаблонов инструмента или напиши минимальный конфиг с нуля по
     документации самого инструмента, если готового шаблона нет под рукой.
   - Подставь РЕАЛЬНЫЕ найденные пути слоёв вместо примерных `src/domain`/`src/infra` из шаблона.
   - Запиши файл в корень проекта (`.dependency-cruiser.cjs`, `.importlinter`, `.go-arch-lint.yml`)
     или `scripts/check-crate-boundaries.sh` (Rust, `chmod +x`).
   - Предложи (НЕ автопатчь) добавление CI-job, проверяющего границы, в существующий CI-workflow
     репозитория — покажи diff, спроси подтверждение отдельно от конфига.
6. **При отказе** — не создавай файл, зафиксируй решение одной строкой в заметках репозитория
   (например, в его собственном README или журнале решений): «Arch-lint предложен, отклонён
   пользователем {дата}» — чтобы повторный онбординг не предлагал то же самое снова.

## Правила

- **Не угадывай конкретные запрещённые пары** сверх обнаруженной пары слоёв — предлагай ровно то,
  что нашёл (`{найденный_layer_A} → {найденный_layer_B}` запрещено), не расширяй список правил
  фантазией об архитектуре, которую не видел в коде.
- **Никогда не патчь существующий CI-workflow автоматически** — только предложение с diff,
  подтверждение пользователя обязательно: изменение CI влияет на все последующие PR всех
  контрибьюторов репозитория.
- **Rust — честная оговорка в самом диалоге с пользователем**, не молчать про специфику:
  ```
  Rust: настоящая граница — это Cargo workspace (компилятор физически не даст domain-крейту
  использовать infra, если тот не в Cargo.toml). Скрипт scripts/check-crate-boundaries.sh —
  дополнительная защита ТОЛЬКО от случая, если кто-то явно пропишет infra в зависимости domain
  в Cargo.toml (компилятор это разрешит, скрипт поймает).
  ```
- **Языковая локализация** — предложение и объяснение пользователю на русском; сами
  конфиги/YAML/имена файлов — на английском (стандарт инструментов).

## Output contract

При успешном создании — одна строка в итоговом отчёте:
```
+ .dependency-cruiser.cjs      — запрет {layer_A}→{layer_B}, запрет циклов
```
(конкретный инструмент и путь — по факту сработавшей ветки; для Rust — путь
`scripts/check-crate-boundaries.sh`, не конфиг-файл).

Если пользователь отклонил — ничего не пишется в отчёт, только одна строка в заметках
репозитория (см. Процесс, шаг 6).
