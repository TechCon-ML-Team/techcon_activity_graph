# Git workflow — коммиты, полномочия на слияние, back-merge

Источник этих правил — `canon/GIT-CONTRACT.md` организации TechCon (§1.1–1.13),
утверждён владельцем. Ниже — операционализация, а не пересказ: что именно
сделать в типовом сценарии и почему нарушение конкретно ломает CI, а не просто
«не по стилю».

## Базовый поток

```
feature/* → PR (squash) → develop → PR (merge-commit) → main → (авто-деплой, где есть)
```

`develop` всегда впереди `main`. Прямые коммиты в `main`, минуя `develop`,
запрещены везде — включая хотфиксы (§1.5): даже экстренное исправление в проде идёт
через `develop`, затем отдельным промоушн-PR в `main`.

## Формат коммита

Заголовок — Conventional Commits: `<type>(<scope>): <summary>`. Список типов
закрыт (каноническая реализация — `cli/techcon_harness/commit_lint.py::ALLOWED_TYPES`):

```
feat fix docs style refactor perf test build ci chore revert
```

Типа вне этого списка не существует — придумывать новый (например
`alerts(...)`) нельзя, коммит-хук отклонит его, а если он уже запушен,
чинится только переписыванием истории. Merge-коммиты (`Merge pull request
#N from ...`) исключены из проверки формата — так генерирует сам GitHub, не
человек.

Агентский коммит несёт трейлер `Co-Authored-By:` с моделью сессии. Один
коммит — одно логическое изменение, не смешивать несвязанные правки.

### Привязка к задаче Linear

Если коммит/PR продвигает конкретную задачу Linear — имя ветки должно
содержать её идентификатор в форме `tml-<id>` (регистр неважен), в идеале —
буквально поле `gitBranchName` из карточки задачи, не придуманное заново имя.

Без отдельной ветки на задачу (мелкое исправление, хотфикс) — трейлер в теле
коммита: `Linear: TML-<id>` отдельной строкой, рядом с `Co-Authored-By:`, но
не смешивая в одну строку.

Не для каждого коммита — служебные/раздаточные коммиты (`[automated]` и
подобные) привязки не требуют, только те, что продвигают содержательную
работу.

## Кто выполняет слияние и как

- Разрешено сливать в `main`/`develop`: владелец-человек или агент — только
  после зелёного CI и явного мандата в задаче/брифе, никогда по собственной
  инициативе молча. Отсутствие запрета в брифе мандатом не является.
- `gh pr merge --admin` запрещён всем без исключений — он обходит
  немногочисленные проверки, которые вообще работают на бесплатном плане
  GitHub.
- `feature/* → develop` — **squash**, там нет проблемы ancestry (ветка
  одноразовая).
- `develop → main` (промоушн) — **merge-commit, НЕ squash**
  (`git merge --no-ff` / `gh pr merge --merge`). Squash здесь создаёт на
  `main` коммит с единственным родителем — старым tip `main`; коммиты
  `develop` не становятся его предками. Гейт K3
  (`verify-promotion-provenance`, ancestry-check
  `git merge-base --is-ancestor origin/develop $SHA`) гарантированно упадёт
  на следующем же цикле — это не стилистическое предпочтение, а прямая
  причинно-следственная связь.
- **`--delete-branch` запрещён на промоушн-PR `develop → main`.** Head
  такого PR — сама постоянная ветка `develop`, не одноразовая feature-ветка:
  удаление базы закрывает все открытые PR, нацеленные на неё. Перед первым
  таким слиянием в репозитории проверить
  `gh api repos/<org>/<repo> --jq .delete_branch_on_merge` — если `true`,
  выключить (`-f delete_branch_on_merge=false`) до слияния, а не после: эта
  настройка удаляет head-ветку при ЛЮБОМ слиянии независимо от флага CLI,
  одного отказа от флага недостаточно.

## Back-merge `main → develop` — после хотфикса

Если `main` получил коммиты в обход `develop` (хотфикс, аварийный прямой
push, вручную экспортированное исправление в проде) — нужен back-merge в
обратную сторону. Это симметричный штатный поток, не «на всякий случай»:
без него инвариант «`develop` всегда впереди `main`» тихо ломается, и
следующий промоушн затирает это исправление.

**Как обнаружить, что момент наступил** — перед КАЖДЫМ промоушном
`develop → main` проверять:

```bash
git fetch origin main develop
git merge-base --is-ancestor origin/main origin/develop
```

Код `1` (не 0) означает: в `main` есть коммиты, которых нет в `develop`.
Это сигнал к back-merge, а не повод форсировать промоушн вперёд — `main` в
этом состоянии стоит ВПЕРЕДИ `develop`, а не позади, форсированный
`develop → main` в этой ситуации либо не пройдёт fast-forward, либо тихо
потеряет прод-коммиты `main`.

**Процедура (дословно):**

```bash
git checkout -b sync/main-to-develop origin/develop
git merge --no-ff origin/main   # merge commit, НЕ squash — см. ниже
git push origin sync/main-to-develop
gh pr create --base develop --head sync/main-to-develop \
  --title "chore: back-merge main -> develop (hotfix sync)" \
  --body "..."   # назвать конкретные коммиты main и почему они там оказались
# после зелёного CI:
gh pr merge --merge   # снова merge-commit, не squash
```

Merge-commit нужен и здесь: squash на этой границе создаёт в `develop`
коммит с единственным родителем — старым tip `develop`, исходные коммиты
`main` не становятся его предками, и повторная проверка предков снова
вернёт `1` — работа формально сделана, инвариант не восстановлен.

Конфликт, который не решается тривиально (не «взять любой фрагмент правки»,
а требует содержательного решения, чья версия правильная) — выносится
владельцу/в PR, не решается угадыванием.

## Отказ — штатный исход

При запросе на нарушение любого из этих правил (прямой push в `main`,
squash-слияние промоушна, `--admin`, `--delete-branch` на постоянной ветке,
слияние без зелёного CI) — отказать и предложить корректный путь: ветка + PR
вместо прямого пуша, merge-commit вместо squash на этой границе, дождаться
CI вместо форсирования. Отказ — не конфликт, а ожидаемое поведение.

Ревёрт живого прод-поведения — изменение прод-поведения, а не техническая
операция; идёт тем же путём (ветка + PR + ревью), что и любое другое
изменение, никогда напрямую.

## Чего этот скилл не решает

Не заменяет полный текст `canon/GIT-CONTRACT.md` организации (§1.1–1.13) —
там разбор инцидентов, обоснования и пограничные случаи, которые сюда
намеренно не перенесены построчно. При расхождении или незнакомом сценарии
сверяться с оригиналом, не достраивать правило по аналогии.
