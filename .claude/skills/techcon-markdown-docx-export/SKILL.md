# Markdown → DocX export

## Цель

Получить стабильный человекочитаемый `.docx`-артефакт из Markdown-источника, не превращая
DocX в источник правды для дальнейшего редактирования.

## Основная команда

Один файл:

```bash
npm run docs:md-to-docx -- INPUT.md OUTPUT.docx
```

Batch-режим для локальной рабочей папки документов:

```bash
npm run docs:md-to-docx
```

Batch-режим по умолчанию читает из `docs/markdown/` и пишет в `docs/docx/` — сверяйте
реальные пути в `package.json` конкретного репозитория, они могут отличаться.

## Правила

- Один Markdown-источник на семейство документа — не плодить несколько `.md`-версий
  одного и того же документа.
- Держать имена `.md` и `.docx` согласованными (общий stem).
- Перегенерировать `.docx` после содержательной правки Markdown, а не откладывать.
- Не редактировать `.docx` руками — любая правка, сделанная напрямую в DocX, будет
  потеряна при следующей перегенерации и разойдётся с источником.
- Если Markdown содержит блоки Mermaid, заранее убедиться, что доступен `npx mmdc`
  (mermaid-cli) — иначе диаграммы не отрендерятся в экспорте.

## Проверка после экспорта

- Убедиться, что файл `.docx` действительно создан (не просто команда завершилась без
  ошибки).
- При необходимости открыть сгенерированный документ и сверить, что заголовки и крупные
  разделы пережили конвертацию — Markdown-специфичные конструкции (вложенные списки,
  таблицы, сноски) иногда теряют форматирование при экспорте.

## Антипаттерны

- Редактировать `.docx` и забыть перенести правку обратно в Markdown — следующий экспорт
  молча затрёт ручную правку.
- Генерировать несколько по-разному названных `.docx`-вариантов из одного источника без
  явной причины — непонятно, какой из них актуален.
- Считать batch-вывод авторитетным, если исходный Markdown устарел — экспорт консервирует
  устаревание, а не исправляет его.
