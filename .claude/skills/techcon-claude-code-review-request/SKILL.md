# Запрос активного ревью

Этот скилл готовит brief для внешнего ревью и запускает активную
диагностику — не просто чтение файлов, а реальная проверка состояния
системы (endpoint'ы, команды, доступы).

## Когда применять

- Перед реализацией для задач с архитектурными решениями
- Когда спецификация задачи включает изменения API, новые зависимости, миграции
- Для периодического reality-check документации репозитория
- По команде пользователя ("сделай критику", "проверь реальность", "найди пробелы")

## Когда НЕ применять

- Мелкий баг-фикс (одна строка)
- Чисто текстовые задачи без архитектурных решений

---

## Шаги

### 1. Определи тип ревью

По контексту задачи:
- `architecture` — новые компоненты, рефакторинг структуры
- `security` — auth, данные пользователей, внешние вызовы
- `critique` — пользователь хочет критику без блокировки
- `reality-check` — проверить соответствие документации реальности
- `knowledge-gap` — найти пробелы в документации/базе знаний
- `full` — комплексный ревью

### 2. Собери контекст задачи

Прочитай проектную документацию репозитория (README, архитектурные заметки,
описание ограничений) и спецификацию задачи, если она оформлена отдельным
документом.

Найди файлы кода, которые затрагивает задача.

### 3. Собери что можно проверить

**Endpoints:** найди в документации, README, docker-compose, nginx-конфигах
все URL сервисов, которые затрагивает задача.

**Команды:** определи что полезно выполнить для диагностики (`git log`,
grep по коду, проверки конфигов, статус сервисов).

**Доступы:** что может понадобиться ревьюеру (SSH-ключи, env vars,
credentials) — перечисли явно, не подразумевай.

### 4. Создай brief

Запиши в `{taskDir}/review-brief.md` (или иное согласованное в проекте
место для артефактов задачи):

```markdown
---
taskId: {taskId}
title: {название задачи}
reviewType: {тип}
status: pending
outputPath: {taskDir}/review-result.md
createdAt: {ISO-8601}
---

# Review Brief — {taskId}: {title}

## Objective

{1-2 предложения: что проверяем и почему важно до реализации}

## Files to read (абсолютные пути)

| Файл | Назначение |
|---|---|
| `/abs/path/README.md` | Архитектура проекта |
| `/abs/path/к/спецификации/задачи` | Спецификация |
| `/abs/path/к/затронутому/файлу` | {описание} |

## Endpoints to verify

| URL | Что проверить |
|---|---|
| `https://{host}/api/health` | Доступность, версия |
| `https://{host}/api/{endpoint}` | Контракт ответа |

(если нет endpoint'ов — оставь таблицу пустой, ревьюер найдёт сам)

## Commands to run

\`\`\`bash
git log --oneline -10
git diff --stat HEAD~5
grep -r "{ключевое слово}" src/ --include="*.py" | head -20
\`\`\`

## Access requirements

- **SSH к {host}** — для проверки {что именно}
- **{ENV_VAR}** — для аутентификации к {сервис}
- (оставь пустым если доступ не нужен)

## Cross-repo context (если задача затрагивает несколько репозиториев)

| Файл | Репозиторий |
|---|---|
| `/abs/path/к/артефакту/в/другом/репо` | {repo} |

(удали секцию если не нужна)

## Questions for review

1. {Конкретный вопрос с контекстом}
2. {Вопрос о рисках}
3. {Вопрос о граничных случаях}

## Already decided (не пересматривать)

- **{Решение}**: {обоснование}
```

### 4b. Ограничь ревьюера рамками ревью

Ревьюер должен только писать в `outputPath` и не трогать код или
спецификацию задачи — иначе роль ревьюера дрейфует в роль допиливателя,
и итог ревью перестаёт быть независимым. Зафиксируй это ограничение прямо
в brief (секция Objective или отдельной строкой) и, если инструмент
ревьюера поддерживает hook/guard на запись файлов, ограничь запись
единственным путём `outputPath`.

### 5. Выведи инструкцию пользователю

Выведи ДОСЛОВНО:

---
**Ревью готово к запуску.**

Передай ревьюеру:
```
Прочитай и выполни протокол ревью:
{абсолютный путь к review-brief.md}
```

Ревьюер проверит endpoint'ы, выполнит команды и запросит доступы если нужно.
После того как он напишет ревью — скажи мне "ревью готово".

---

### 6. Жди сигнала

После "ревью готово" — продолжи работу приёмом результата ревью
(извлеки verdict из результата и действуй по нему: approved / changes-requested
/ needs-discussion / critique).

## Output contract

- Файл `{taskDir}/review-brief.md` создан с абсолютными путями
- Секции `Endpoints`, `Commands`, `Access requirements` заполнены
- Ревьюер ограничен записью только в `outputPath`
- Пользователь получил инструкцию с точным путём к brief
