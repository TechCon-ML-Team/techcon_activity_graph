# Выгрузка алертов мониторинга

Используй этот скилл, когда нужно получить последние N алертов экосистемы TechCon —
для диагностики инцидента, сводки за период или проверки, замолчал ли алерт после фикса.
Применим из любого репозитория TechCon, не привязан к конкретному репозиторию вызова.

## Источник истины

Алерты доставляются на почту (alertmanager → e-mail). Почтовый ящик — первичный источник.
Правила алертов (пороги) живут в репозитории/сервисе мониторинга целевой экосистемы —
конкретное расположение уточняй в текущем проекте, не подставляй запомненное значение.

| Источник | Назначение |
|---------|-----------|
| Почта (alertmanager) | фактические срабатывания со временем |
| Правила алертов (мониторинг-стек: Prometheus/Alertmanager/Grafana) | пороги, что мониторится |

## Шаги

1. **Подключись к почтовому источнику** (read-only). Доступ/креды бери из переменных
   окружения или менеджера секретов проекта — никогда не хардкодь в команде.
2. **Выгрузи последние N** писем-алертов (по умолчанию N=20), отсортированные по времени
   (новые сверху). Фильтр по отправителю/теме alertmanager.
3. **Нормализуй каждый алерт** в структуру:
   - `time` — время срабатывания (ISO, локаль оператора)
   - `status` — firing / resolved
   - `alertname` — имя правила
   - `target` — сервис/ВМ/инстанс
   - `severity` — critical / warning / info
   - `details` — краткое тело (что превышено, значение vs порог)
4. **Сгруппируй по `alertname`+`target`** — покажи firing↔resolved пары (сколько раз
   срабатывал, замолчал ли). Открытые (firing без resolved) — выделить.

## Минимальный вывод

Таблица последних N алертов: `time | status | alertname | target | severity | details`.
Плюс краткая сводка: сколько открытых (firing), сколько резолвилось, какие повторяются.
Если источник пуст/недоступен — зафиксируй явно («ящик недоступен: {причина}»), не выдумывай.

## Анти-паттерны

- Пересказ «алертов много» без конкретных строк со временем/статусом.
- Игнор resolved-событий — без них не видно, замолчал ли алерт после фикса.
- Хардкод кредов почты в команде (shell history) — только через переменные окружения/секрет-менеджер.
- Подмена почтового источника догадкой по логам сервиса (это другой сигнал).
