# Авторство внешних отчётов (менеджмент/руководство)

Портируемая директива, не программа. Исполняется обычными командами оболочки
и чтением файлов, без вызовов, специфичных для конкретного агентного
harness'а. Применима к любому репозиторию организации.

## Goal

Два разных документа для двух разных аудиторий — Markdown-отчёт для
менеджмента и HTML-дашборд для руководства — так, чтобы КАЖДОЕ ЧИСЛО было
проверяемым фактом, а ПОДАЧА (нарратив, структура, визуализация) была живой
для конкретного периода/проекта, не заполнением слотов одного шаблона.

## Область действия

**Делает:** Markdown-отчёт для менеджмента (при необходимости — в `.docx`;
Markdown сам по себе не финальная форма сдачи, а трассируемый источник
текста); HTML-дашборд/кейс для руководства. Оба — по организации, по одному
проекту или по группе проектов.

**НЕ делает:** не считает числа сам (работа отдельного детерминированного
скрипта сбора метрик), не решает, нужен ли отчёт вообще (решение человека),
**не додумывает смысл за пользователя** — см. Фазу 0.

## Фаза 0 — Уточнение области и контекста (ОБЯЗАТЕЛЬНА, до Фазы 1)

Живая находка: агент написал в отчёте «X не закрыт — открытый вопрос»,
взяв формулировку дословно из внутреннего трекера состояния. Владелец
поправил: это было оставлено НАМЕРЕННО, по прямой просьбе — код и документ
этого не говорят, потому что не обязаны нести историю решения, только его
следствие. **Данные показывают ЧТО произошло, не всегда ПОЧЕМУ и не всегда
что из этого действительно важно показать читателю.** До письма — не после
— агент обязан закрыть такие разрывы вопросом, а не догадкой.

Спросить пользователя (с конкретными вариантами ответа, если они есть)
ОБЯЗАТЕЛЬНО, если:
- **период не назван** — с основания проекта, за квартал, за спринт?
  Предложить варианты, не выбирать самому;
- **масштаб неоднозначен** — один проект, группа проектов, организация;
- **у наблюдаемого состояния может быть скрытая причина** — выглядит как
  «не сделано»/«баг», но источники не говорят, было ли это решение
  осознанным. Не приписывать причину без подтверждения — либо спросить,
  либо описать наблюдение без причины;
- **раздел «куда движемся» просится в отчёт, но нет источника, ЧТО там
  значимого** — git-история показывает прошлые эксперименты, не обязательно
  текущий фокус. Спросить прямо, не заполнять универсальными фразами;
- **нужна метрика без чистого вычислимого определения** (например «число
  экспериментов») — спросить, что считать единицей и откуда брать, не
  изобретать подсчёт молча.

Если источники дают уверенный, непротиворечивый ответ — не спрашивать ради
формы; вопрос — когда РЕАЛЬНО неопределённо. Каждый заданный и отвеченный
вопрос — часть Minimum output, чтобы следующий прогон не переспрашивал молча.

## Read order

1. Самый свежий файл с посчитанными числами (`figures-*.yaml` или
   эквивалент) для нужного масштаба — единственный источник чисел. Если
   файла нет или он старше данных — сначала пересчитать (Фаза 1).
2. Предыдущий отчёт ТОГО ЖЕ типа, если есть — чтобы не повторить структуру и
   формулировки слово в слово. Копирование прошлой прозы — антипаттерн.
3. Действующий брендбук репозитория/организации — для HTML: единственный
   источник цвета/шрифта; использовать буквально, не «улучшать» по памяти.
4. Файл дизайн-токенов и шрифтовые ассеты, если есть — встраивать шрифт как
   base64 в `@font-face`, не ссылаться на путь на личном диске автора.
5. Правила цензуры утечек для внешних документов, если такой список есть.
6. Для per-project кейса — сам репозиторий: `git log`, `README.md`, файл
   текущего состояния проекта, если есть.

## Фаза 0б — Глубина исследования для нового/полноисторийного кейса

Живая находка: поверхностный однопроходный `git log` дал 3 вехи на
репозиторий с 852 коммитами за 288 дней, хотя реальных крупных переработок
было минимум 12-18. Один проход по «хвосту» истории систематически
недооценивает объём работы за пределами последнего всплеска.

Если кейс покрывает **весь период с основания проекта** или несколько
месяцев истории — **параллельное исследование по нескольким фронтам
ОБЯЗАТЕЛЬНО**, не на усмотрение агента:
- вехи месяц за месяцем по всей истории, порог ~1 веха на 4-6 недель для
  активного проекта; явно отмечать месяцы без вех (это факт, не пробел);
- для инфраструктурных кейсов — отдельный фронт по истории затрат/
  оптимизаций, отдельный по структуре системы на сегодня;
- параллельные потоки, не последовательные ручные проходы — иначе цена
  глубины непропорционально велика;
- числа, которые владелец сообщает напрямую (без следа в git) —
  использовать с атрибуцией «подтверждено владельцем», не отбрасывать
  из-за отсутствия корпоративных доказательств.

Для короткого явно ограниченного периода (спринт, релиз) это правило не
действует — истории мало по определению.

Второй живой урок: исследование дважды упускало крупный пласт продукта —
(1) фильтр вех по conventional-commit префиксу не ловит веху, названную
иначе (`Stage 2a: ... (#99)`) — прогонять поиск и без якоря на префикс, и
отдельно топ коммитов по объёму diff; (2) заранее данный список файлов
(README, «паспорт проекта») — только отправная точка, не исчерпывающий
список: обязателен независимый шаг — перечислить ВСЮ документацию и хотя бы
бегло увидеть даты каждого файла; дата старше половины истории репозитория
— сигнал перепроверить актуальность, не цитировать как текущее состояние.

## Фаза 1 — Факты (код, не агент)

Числа считает отдельный детерминированный скрипт сбора метрик репозитория
(org-масштаб и per-project вариант с параметром слага), не агент по памяти.

Если числа нет ни в файле с фактами, ни в выводе скрипта — задача НЕ
«придумать по смыслу», а решить: (а) число не нужно отчёту, (б) скрипт
стоит расширить новым полем (отдельная правка кода), (в) число получается
только ручным замером — тогда с явной пометкой «оценка»/«ручной замер» и
командой проверки в сноске, не наравне с прочими фактами.

## Фаза 2 — Нарратив

Не заполнение слотов шаблона. Перед письмом — что здесь ГЛАВНОЕ в этом
периоде/проекте, структура строится вокруг этого, не вокруг фиксированного
списка секций. SCQA (Ситуация → Осложнение → вопрос → Ответ) — рабочий
каркас, не обязательная буква. Честно, не смягчая формулировки, если
источник сам называет вопрос открытым.

Правило: качественная формулировка (не число) свободна; число — только из
файла с фактами, дословно или как округлённый процент.

## Фаза 3а — Markdown-отчёт (менеджмент)

Обязательные смысловые блоки (без фиксации порядка/формулировок): ситуация/
контекст → что сделали (вехами, без хирургически точных дат, если не
попросили иначе) → результат на сегодня числами → что не решено → куда
движемся дальше (по факту Фазы 0) → всё. Полные смысловые названия, не
технические id. Никакой методологической риторики о происхождении чисел в
теле («оценка», сноски проверки) — вся сверка делается в Фазе 4, не
демонстрируется читателю. Конкретные метрики обязательны, не только число
коммитов. Тон — про эффективность и качество работы команды, не «вау-
эффект» (это роль HTML). Перед сдачей — проверить себя по правилам цензуры
утечек (внутренние хосты, IP, пути, хеши недопустимы).

## Фаза 3б — HTML-дашборд/кейс (руководство)

Файл дизайн-токенов — источник цвета/шрифта, НЕ каркас вёрстки: layout и
состав визуализаций агент решает заново под контент. Тема — та, что
зафиксирована брендбуком для этой аудитории. Числовых/графических элементов
должно быть заметно больше, чем прозы: таймлайн, хотя бы одна диаграмма по
реальным данным, крупные цифры-бейджи. Для графиков по умолчанию — простой
ручной SVG; библиотека (проверенный CDN, версия закреплена) — только если
данных действительно много. Один файл, self-contained: брендовый шрифт —
base64 в `@font-face`, системные шрифты — через официальный CDN шрифтов,
никаких прочих внешних подключений. Никакой технической/операционной
механики (CI/PR-числа, разбивка коммитов, внутренние хосты) — здесь посыл
и архитектура простым языком. Раздел «куда движемся» — по факту Фазы 0,
без внутренних тикетов. Отделять подтверждённое замером от заявленного
свойства без живого кадра — псевдо-скриншот не рисовать, заменять честной
схемой без пояснений о происхождении.

**Паттерны/антипаттерны для HTML-кейса**, накопленные по опыту нескольких
прогонов:
- заголовок утилитарный, не метафора; жаргонный термин — оставлять, рядом
  простое объяснение в 1 фразе;
- собственную работу — через выбор и добавленную ценность, не
  самоуничижение («ансамблевая модель из лучшего», не «просто дообучили»);
- для зрелых направлений — акцент на исследовательскую ценность (гипотезы,
  эксперименты, включая провалившиеся); для молодых — на инженерную
  скорость и первый результат;
- прогресс — явное «было / стало» с числами по обе стороны;
- карточки — сеткой/вертикально, никогда горизонтальным скроллом;
  насыщенные темы дробить на несколько карточек;
- ограничения внешних систем — явно отдельно от возможностей продукта, не
  сливать в одно утверждение;
- шаблонные «нейроночные» обороты («не X, а Y» кластерами, пустые звучные
  институциональные фразы) — под запретом; один точечный контраст — норма,
  серия подряд — признак генерируемого текста;
- домен/предметную область — проверять с владельцем буквально, не
  наследовать из черновика без сверки;
- техническую метрику качества (0–1) не подписывать как процент точности.

**Три правила владельца, главнее списка выше при конфликте:**
1. **Не стрелять себе в ногу.** Находка — заголовком идёт построенная
   способность обнаруживать/предотвращать («разработали механизм X,
   который нашёл Y»), не признание промаха. Цифру эффекта не искажать —
   искажается только фокус подачи.
2. **Без текстового нейрослопа.** Плюс: абстрактно-институциональные
   конструкции без субъекта («оценка владельца») — команда говорит от
   своего лица («по нашим расчётам»).
3. **Технологичность — раскрывать широко, простым языком**, не
   перечислением названий API; каждый архитектурный выбор — с явным
   «зачем», не только описанием структуры.

Острее применяют правило 1, не новые правила: раздел из одной самокритики
не спасает позитивные заголовки карточек — разбавлять находками ВОВНЕ, не
только внутри своего проекта; простои/красный CI не входят в хронологию
вех (веха = прогресс); провальная гипотеза, о которой команда просит
молчать, — вырезается целиком, не переформулируется позитивно; название-
эвфемизм для внутреннего механизма — тот же нейрослоп, заменять прямым
описанием сути; иноязычные заимствования — грепать и убирать; график
«улучшается со временем» — только на реально верифицированной динамике, не
подменять запрошенную метрику другой молча.

## Фаза 4 — Самокритика до показа человеку

- Каждое число трассируется на конкретный `id` в файле с фактами (дословно
  или `round(value*100)%`). Число без id — удалить или получить отдельно.
- Нарратив не повторяет прошлый отчёт того же типа слово в слово.
- Открытые вопросы источника поданы так же прямо, как в источнике.
- Проверка утечек для внешних документов пройдена вручную.
- Каждый CSS-класс в разметке HTML реально определён — в дизайн-ките или в
  `<style>` файла. Живой сбой: классы использовались в разметке, но нигде
  не определены — унаследованы копипастой из старого черновика. `grep -o
  'class="[^"]*"'` по телу → сверить каждый класс с определениями — до
  предъявления, не после жалобы на внешний вид.

## Приложение — задача трекера для секции «Лог работ»

```
[Область] Название — про РЕЗУЛЬТАТ/ЦЕЛЬ, не про текущее состояние
          («ждёт решения» — в поле Статус, не в заголовке)

Что и почему: 2-4 предложения, простым языком.
Как: подход/метод простыми словами.
Сделано: конкретные пункты.
Осталось: конкретные пункты.
Статус на <дата>: отдельной строкой, меняется со временем.
Когда: ключевые даты.
```

Одна задача = один ID трекера на всё время жизни; обновление — комментарий/
строка в ту же карточку, не новая карточка. Для регулярных однотипных
случаев — формат «Пакет»: одна карточка на проект и период, лог внутри
дописывается, не пересоздаётся; язык — менеджерский, без внутренних имён
технических механизмов.

## Working rules

- Новый рендер — зафиксировать в реестре/манифесте экспортов репозитория,
  если он есть.
- Рендер с headline-числами — добавить в тест трассировки фигур, если он
  есть (можно ограничить набор id, если HTML показывает не всё из `.md`).
- Markdown → DocX через скрипт конвертации репозитория, если он есть.
- HTML для git и для инструмента рендера артефактов одновременно —
  использовать только проверенный CDN для скриптов и официальный CDN
  шрифтов, чтобы один файл работал в обоих местах без развилки.

## Authority rules

- Файл с фактами — единственный источник числа; расхождение с памятью
  агента правится в тексте, число не выдумывается.
- Файл дизайн-токенов — единственный источник цвета/шрифта для HTML;
  устаревший CSS-файл старой отчётности не использовать.
- Действующий брендбук — источник истины по бренду поверх памяти агента.

## Minimum output

По итогу агент обязан явно перечислить: путь к использованному файлу с
фактами (и нужна ли была пересборка); путь к написанному `.md`/`.docx`/
`.html`; какие вопросы заданы в Фазе 0 и какие ответы получены; какие числа
расходятся с предыдущим отчётом того же типа и почему; что добавлено в
реестр/тест трассировки, если они есть; какие утверждения даны как оценка,
а не измеренный факт, и как это проверить.

## Anti-patterns

- Число без соответствия в файле с фактами, включая округление «на глаз».
- Утверждение причины наблюдаемого состояния без подтверждения источником
  или пользователем.
- Молчаливое заполнение раздела «дальше»/метрики без чистого определения
  вместо вопроса пользователю.
- Методологическая риторика о происхождении чисел в теле отчёта.
- Копирование структуры/формулировок прошлого отчёта один в один.
- Фиксированный порядок секций одинаковый для каждого отчёта независимо от
  содержания периода.
- Смягчение честного открытого вопроса источника ради впечатления — но
  сперва убедиться, что это правда открытый вопрос, а не решение, которое
  не записали.
- Забытая правка реестра/манифеста после нового рендера.
- Устаревший файл стилей или неверная тема (тёмная/светлая) для HTML.
- Псевдо-скриншот интерфейса вместо честной схемы без реального кадра.
- Горизонтальный скролл для последовательности карточек.
- Самоуничижительное описание своей работы вместо формулировки через выбор
  и добавленную ценность.
- Кластеры «не X, а Y» и звучные пустые институциональные фразы.
- Домен/предметная область из прошлого черновика без проверки с владельцем.
- Техническая метрика качества (0–1), поданная как процент точности.
