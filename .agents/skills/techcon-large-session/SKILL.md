# Большие сессии: Workflow / techcon-fanout вместо цепочки агентов

Используй этот скилл, когда следующий шаг задачи распадается на несколько
независимых частей и стоит выбор: делать последовательно одним агентом за
раз, или запустить параллельный фанаут. План программы (D19) называет это
обязательным по умолчанию для трёх случаев — не рекомендацией «когда
удобно».

## Когда фанаут обязателен по умолчанию (D19)

1. **Adversarial-критика только что сделанного.** Несколько ревьюеров с
   разными линзами ОДНОВРЕМЕННО на свежем контексте, не один ревьюер за
   раз и не последовательная цепочка.
2. **Параллельное исследование следующего шага.** Несколько независимых
   развилок/PoC-вопросов — одновременный fanout read-only
   scout-исследователей, не последовательный перебор.
3. **Периодический полный аудит репозитория** перед крупными вехами
   (G2/G5/W0 и аналогичными) — отдельный проход «аудит всего», не точечная
   критика одного PR.

## Что НЕ превращать в фанаут

Мелкие последовательные фиксы одного файла, точечный повторный прогон
одного упавшего теста, single-file верификация после мелкой правки —
оверкилл, один агент или напрямую. Не дробить без нужды на подпроходы —
бюджет не безлимитный (квота личных подписок на PoC/демо/Workflow/fanout).

## Выбор инструмента: Claude Workflow vs Codex techcon-fanout

| | Claude Workflow | Codex techcon-fanout |
|---|---|---|
| Где искать шаблоны | `workflows/claude/{review-branch,audit-standard,research-fanout,implement-dag}.js` | `workflows/codex/techcon_fanout/` (7 шагов: plan→run→state+resume→barrier→verify→integrate→reap) |
| Плановый потолок | до 30 агентов за прогон (D5, целевая цифра плана — НЕ проверенный технический лимит инструмента) | — |
| Лимит инструмента (проверено) | `min(16, cpus-2)` одновременно, 1000 всего за время жизни сессии (P10) | `max_concurrent_threads_per_session=6` |
| Изоляция записи | `isolation:"worktree"` у write-агентов | worktree на задачу (`runner.worktree_for`) |
| Резюмируемость | нет встроенного resume между прогонами | да — `task_sha256` + `state.jsonl` |

Выбирай Workflow, если работа в рамках одной Claude Code сессии и не нужен
resume между отдельными запусками. Выбирай techcon-fanout, если задачи
DAG-зависимы, могут растянуться на несколько прогонов (нужен resume), или
явно код-ориентированы через Codex.

## Шаги

1. **Оцени количество независимых частей.** ≥4 — фанаут обязателен по
   умолчанию (D19), если это один из трёх случаев выше; <4 — обычно
   оверкилл, см. «Что НЕ превращать в фанаут».
2. **Проверь `route.py` (D4).** `fanout_recommended: true` при ≥4
   независимых частях — не изобретай порог заново, `route.py` уже несёт
   его как единственный источник (`roles/builder.yaml#fanout.
   fanout_recommended_threshold`).
3. **Выбери шаблон/инструмент** по таблице выше — не пиши новый Workflow с
   нуля, если существующий шаблон покрывает случай (review-branch —
   ревью PR; audit-standard — сверка с реальными данными; research-fanout
   — параллельное исследование; implement-dag — DAG-зависимые реализации).
4. **Явный стоп мутаций для read-only части.** Если часть агентов —
   scout/ревьюер (не должны писать), это фиксируется в брифе
   (`templates/brief.schema.json#read|write`), не полагается на то, что
   агент «сам не будет».
5. **После завершения — не пропускай верификацию.** И Workflow-шаблоны, и
   techcon-fanout несут собственную Verify-фазу/шаг (независимый
   ревьюер/reviewer, не то же самое, что исполнитель) — не считай задачу
   готовой без неё.

## Анти-паттерны

- Последовательная цепочка одиночных вызовов агента там, где план явно
  требует параллельный фанаут (D19) — теряет как минимум одну из двух
  выгод (независимость перспектив ревьюеров ИЛИ время).
- Изобретение нового Workflow-скрипта с нуля для случая, который уже
  покрывает существующий шаблон в `workflows/claude/`.
- Фанаут на <4 частей ради самого факта параллелизма — тратит бюджет без
  выгоды (см. «Что НЕ превращать в фанаут»).
- Пропуск Verify-фазы/шага после параллельной реализации — фанаут ускоряет
  ИСПОЛНЕНИЕ, не отменяет необходимость независимой проверки результата.
