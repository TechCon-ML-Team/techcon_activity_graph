# Доступ к мониторингу Grafana

Используй этот навык, когда нужно получить живую истину из слоя мониторинга, а не пересказать старые брифы, документы или обсуждения в issue/PR.

## Локализация выходных артефактов

Все итоговые отчёты, сводки для оператора и передачи по этому навыку должны быть написаны на хорошем русском языке.

На английском допускаются только:
- пути;
- URL;
- команды;
- имена файлов;
- формальные идентификаторы;
- названия технологий и аббревиатуры.

## Когда навык ОБЯЗАТЕЛЕН

Используй его, если задача включает хотя бы одно из следующих:
- проверку живой доступности, сигналов, алертов, дашбордов или запроса к источнику данных через Grafana;
- разбор расхождения между доской, конфигурацией проверок, runbook и текущим статусным отчётом;
- поиск дублирующих, устаревших или ложных поверхностей мониторинга;
- подготовку передачи оператору, где надо явно указать, чему верить в первую очередь;
- любой вывод о состоянии `dev` или `prod`, который нельзя обосновать только текстом из репозитория.

## Главный принцип

Мониторинг полезен только тогда, когда он даёт одну рабочую истину, а не несколько конкурирующих картин.

Не считай дашборд, текстовый документ и старый отчёт равными по силе источниками. Сначала считывай живой слой Grafana и мониторинга, затем проверяй слой владельца поверхности, и только потом сопоставляй это с документами и прошлыми передачами.

## Короткий словарь

- **слой владельца** — кто отвечает за эту поверхность: рантайм, которым владеет репозиторий, публичный слой публикации или общий канал для оператора;
- **слой правил и приёмки** — issue/задача, отчёт, вердикт по фазе и другие артефакты, которые говорят, что именно считается принятым;
- **содержательный слой** — факты о реальной работе дашбордов, алертов, проверок и запросов к источникам данных;
- **оставшийся дрейф** — конкретное расхождение, которое ещё не сведено между живой системой, репозиторием и передачей.

## Порядок сбора фактов (research-first)

Перед любым выводом собери минимальный, но достаточный набор фактов в таком порядке:

0. **Проверка перед стартом**
   - какой базовый URL Grafana или стек читается;
   - какой `org` или tenant используется;
   - какой UID источника данных или другой целевой источник участвует в выводе;
   - какой временной диапазон выбран;
   - в какой момент был снят результат.

1. **Живая истина Grafana**
   - какие дашборды, алерты, инциденты и результаты запросов к источникам данных существуют сейчас;
   - какие названия, UID, папки, метки и владельцы видны прямо в системе;
   - какие сигналы активны сейчас, а какие только исторически описаны.

2. **Истина пакета мониторинга**
   - какие поверхности в текущей работе считаются основными;
   - какие поверхности уже были помечены как спорные, дублирующие или устаревшие;
   - где слой правил и приёмки уже расходился с содержательным слоем.

3. **Истина документов**
   - какие runbook, страницы архитектуры и пакеты передачи описывают ожидаемую картину;
   - где документы являются только пояснением, а не живым доказательством.

4. **Контракт владельца**
   - какой репозиторий и какой слой владеет этой поверхностью;
   - это рантайм-истина, которой владеет репозиторий, публичный слой публикации или общий канал для оператора;
   - какой дрейф остаётся незакрытым и кто обязан его закрывать.

Во всех заметках ЯВНО разделяй:
- факты из живой системы;
- выводы по сопоставлению;
- открытый дрейф;
- неподтверждённые предположения.

## Проверка доступности перед стартом

Этот навык обязателен только если у сессии есть **хотя бы один** исполнимый путь чтения к живому слою мониторинга:
1. Grafana MCP;
2. безопасный аутентифицированный путь через HTTP API;
3. другой явно подтверждённый живой канал чтения оператора, который сильнее текста и устаревших снимков.

Если ни один путь не подтверждён, навык переходит в деградированный/ручной режим:
- не делать вердикт о статусе/здоровье;
- не притворяться, что истина мониторинга прочитана;
- разрешён только отчёт о пробелах:
  - какого доступа не хватает;
  - какой владелец должен его дать;
  - какое именно живое чтение нужно для следующего шага.

## Иерархия истины

По умолчанию используй такую иерархию:

1. **Живой запрос к Grafana / бэкенду мониторинга** — основной источник для текущего состояния.
2. **Конфигурация проверок и контракт мониторинга, которым владеет репозиторий** — основной источник для ожидаемой схемы сигналов.
3. **Статусная задача / передача / отчёт** — источник для вердикта по правилам и границ владельца.
4. **Документация и текст** — подтверждающий, но не первичный источник.

Если дашборд противоречит документам, НЕ исправляй вывод в пользу документов. Зафиксируй дрейф и укажи, какой слой сильнее:
- для текущего статуса сильнее живая истина Grafana;
- для ожидаемого контракта сильнее контракт мониторинга, которым владеет репозиторий;
- для приёмки фазы сильнее слой правил/передачи.

## Когда использовать MCP, а когда HTTP API

### Предпочитай Grafana MCP, если нужно
- быстро найти дашборды, алерты, папки и сводки;
- получить снимок текущей картины, готовый для оператора;
- пройти по нескольким поверхностям мониторинга без ручной сборки HTTP-вызовов;
- сократить число ручных шагов и не плодить локальные обвязки.

### Переходи на Grafana HTTP API, если
- MCP не даёт нужный ресурс, фильтр или уровень детализации;
- надо доказать конкретный UID, правило алерта, запрос к источнику данных или метаданные владения;
- есть подозрение, что проблема не в Grafana, а в обвязке MCP или неполной поверхности инструментов;
- нужно fail-closed перечитывание того же объекта другим путём.

### Если ни MCP, ни HTTP API не доступны
- не считай это мелкой технической помехой;
- не делай вид, что документы или прошлый отчёт заменяют живое чтение;
- выдай только отчёт о пробелах и запрос на доступ или перечитывание владельцем.

### Правило выбора
- Сначала используй MCP как основной канал чтения, если он реально доступен.
- Если вывод существенно влияет на решение владельца, вердикт по фазе или разбор инцидента, перепроверь спорные места через HTTP API, если он реально доступен.
- Если MCP и HTTP API расходятся, НЕ выбирай удобный ответ. Зафиксируй конфликт как дрейф между поверхностью инструментов и слоем доступа, запрети вердикт о статусе/здоровье и запроси повторную проверку владельцем или третье независимое подтверждение.
- Если доступен только один путь чтения, зафиксируй это ограничение прямо в пакете доказательств.

## Fail-closed правила

- НЕ объявляй дашборд канонической истиной только потому, что он красивый или знакомый.
- НЕ считай отсутствие сигнала доказательством здоровья, если не подтверждены источник данных, семантика обновления и поверхность владельца.
- НЕ выполняй мутацию дашбордов, алертов или папок без явного подтверждения человеком.
- НЕ делай вид, что документы подтверждают рантайм.
- НЕ смешивай публичный слой публикации и прямой слой мониторинга/рантайма в один вывод.
- Если доступ через MCP или API неполон, говори: «истина не доказана», а не «проблем нет».

## Как искать дубли и ложные сигналы

Проверяй каждую поверхность по пяти вопросам:

1. Какой вопрос она должна отвечать оператору?
2. Это основной сигнал, вспомогательный сигнал или исторический хвост?
3. Есть ли другая поверхность, которая отвечает на тот же вопрос точнее или быстрее?
4. Совпадают ли названия плиток, проверок, маршрутов и терминов runbook?
5. Может ли эта поверхность показывать красный статус из-за устаревшей смысловой схемы, а не из-за реального сбоя?

Признаки плохой поверхности:
- она дублирует другую доску без новой информации;
- она смешивает боевые и демонстрационные сигналы на одном уровне;
- её названия не совпадают с текущим контрактом проверок или маршрутов;
- она ссылается на несуществующие проверки или старые имена;
- оператору всё равно нужна ручная сверка в другом месте, чтобы понять, реально ли что-то сломано.

## Как сокращать поверхность для оператора

По каждой найденной поверхности дай одно из четырёх решений:
- **оставить основной** — это первая точка входа для боевой проверки;
- **оставить вспомогательной** — полезна только как подтверждение;
- **объединить** — вопрос уже должен жить в другой канонической поверхности;
- **убрать** — поверхность больше не должна участвовать в разборе.

Хороший результат — не больше поверхностей, а меньше путей, по которым оператор может ошибиться.

## Что должно попасть в результат

Выход этого навыка ДОЛЖЕН быть полезен оператору, а не только автору исследования.

В результате зафиксируй:
- какие поверхности Grafana/мониторинга сейчас канонические;
- какие признаны вторичными, дублирующими или устаревшими;
- где смотреть в первую очередь при проверке боевой доступности;
- какой слой владельца у каждой важной поверхности;
- какой оставшийся дрейф остаётся между дашбордом, проверками, документами, слоем публикации и передачей;
- что доказано живым чтением, а что только сопоставлением с репозиторием.

### Шаблон пакета доказательств
1. цель проверки;
2. базовый URL или стек;
3. `org` или tenant;
4. UID источника данных;
5. временной диапазон и момент чтения;
6. живая истина Grafana;
7. канонические поверхности;
8. вторичные или ложные поверхности;
9. слой владельца;
10. оставшийся дрейф;
11. следующий узкий пункт действия без расширения области.

## Режим валидатора и передача, подкреплённая репозиторием

Если работа идёт в режиме валидатора или готовится передача, подкреплённая репозиторием:
- не ограничивайся описательными формулировками;
- отделяй «содержимое принято» от «пакет принят» и от «неизменяемое доказательство принято»;
- явно указывай, где вывод основан на живом чтении мониторинга, а где только на пакете передачи/документов;
- не повышай вердикт только потому, что пакет хорошо написан;
- если публичные документы или отчёт спорят с живой системой, фиксируй это как дрейф правил/пакета, а не как мелкую неточность.

## Антипаттерны

- Читать только бриф и делать вывод о текущем состоянии без живого запроса к мониторингу.
- Считать публичный сайт документации источником текущей боевой истины.
- Оставлять несколько досок «на всякий случай», когда они отвечают на один и тот же вопрос.
- Смешивать Grafana, Homer, Alertmanager, Gatus, GlitchTip в один неразличимый слой без ранжирования по силе сигнала.
- Объявлять зелёный статус только потому, что одна доска не показывает красное.
- Лечить дрейф переписыванием текста, не называя, какой дашборд или проверка устарели.
- Писать передачу без границ владельца и без списка оставшихся расхождений.

## Никогда не делай этого

- НЕ создавай вторую «сводную истину» в тексте, если система уже имеет каноническую поверхность.
- НЕ подменяй живое чтение мониторинга чтением старых issue, PR или markdown.
- НЕ обещай, что истина мониторинга закрыта, если остаются несведённые поверхности владельца.
- НЕ скрывай неопределённость за формулировками вроде «в целом всё выглядит нормально».
